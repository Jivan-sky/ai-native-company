# 技能: anc-distill-targets

## 使用方式

接在 `anc-distill` 阶段 0：先定对象与维度，再动手蒸。

```
/anc-distill-targets <待蒸对象> [业务域]
```

## 功能描述

ANC 管的不是「文件」，是**对象**：人、岗位、团队、业务域、流程、项目、系统。

不同对象的必填维度差别很大。用一套模板硬套，结果是维度虚高、看着很全、执行不了。
本技能给出一张对象表：每类要哪些维度、最小证据集是什么、哪些话**不许写**。

## 对象表

| 对象类型 | 必填维度 | 最小可核验证据 | 不许写 |
|---|---|---|---|
| 人 / 角色 | 职责与边界 · 心智模型 3–7 · 决策启发式 5–10 · 表达特征 · 价值观与反模式 · 内在张力 · 诚实边界 | ≥2 个**不同场景**的可定位原文 | 真实想法断言、性格诊断、隐私、心理评估 |
| 公众人物 | 同「人」，但只用公开材料 | 可公开检索的来源 ≥2 | 私人生活推测、政治立场推演 |
| 业务专家 | 领域判断规则 · 判停标准 · 常见误判 · 依赖的数据与工具 · 责任边界 | ≥1 次完整判断过程的记录 | 把个人偏好写成部门规则 |
| 团队 / 业务域 | 目标与口径 · 角色分工 · 交接物 · 现行规则 · 例外与升级路径 · 术语表 | 一次真实交接或一次真实例会 | 未经确认的口径、部门墙内传闻 |
| 流程 / 作业 | 触发条件 · 输入 · 步骤与分支 · 判停 · 失败恢复 · 输出与验收 | 至少走通一遍的真实记录 | 只写正向流程（缺失败分支 = 不合格） |
| 项目 | 目标 · 阶段 · 干系人 · 里程碑 · 当前状态 · 风险 · 决策记录 | 立项材料 / 周报 / 评审任一 | 把未发生的计划写成已发生 |
| 在册 / 组织 | 人 · 岗 · 权 三列 + 授权来源 + 有效期 | 授权记录（谁授的、给谁、多久） | 无授权来源的权限条目 |
| 系统 / 工具 | 入口形态 · 观测落点 · 句柄 · 权限 · 放行方式 | 至少一次真实探测，或官方文档定位 | 只凭传闻的接口能力 |
| 关系 | 双方 · 互动模式 · 触发点 · 破裂条件 · 修复方式 | ≥2 次具体互动 | 替对方表态 |
| 时刻 / 事件 | 时间 · 地点 · 参与者 · 发生了什么 · 为何重要 · 可复用结论 | 亲历记录或参会记录 | 事后合理化 |
| 地点 / 场景 | 位置 · 功能 · 惯例 · 禁忌 · 关联人 | 实地到过，或多次被提及 | — |
| 记忆 / 偏好 | 触发情境 · 偏好内容 · 强度 · 例外 · 时效 | 重复出现 ≥2 次 | 把单次行为当偏好 |

维度是「必填下限」，不是上限。没证据的维度**留空并标注**，不要凑。

## 知识域怎么打包

一个业务域 = **1 个域路由入口 + N 个原子能力卡**。

- 域路由入口只负责「从哪个话题进哪个能力」，不承载具体方法；
- 可发现入口软预算 **8**（含域入口本身），超了就降级为能力卡；
- 域包必须能独立回答四件事：要什么输入、谁负责、例外找谁、去哪查口径。

域包骨架：

```
out/<域>/
├── SKILL.md        域路由入口
├── cards/          原子能力卡
├── glossary.md     术语表（口径唯一来源）
└── roster.md       人 · 岗 · 权
```

## 授权与红线

1. **先授权，后蒸馏**：写清谁授的权、范围多大、有效期多久；没有授权来源的对象不蒸。
2. 不蒸馏政治人物。
3. 不采集与工作无关的个人信息；个人 agent 的数据只在本人授权范围内流动。
4. 公开仓要脱敏：不放真名 / 机器名 / 账号 / token / 本机绝对路径。
5. 产物必须明确标识「这是蒸馏产物，不是本人」，避免被当成真人表态。
6. 有矛盾就保留矛盾并定位，**不要替对象消解矛盾**。

## 与 ANC 的接口口径

- 「业务域」是 ANC 的第一级隔离字段，**字段本身可自定义**（对齐多维表格 / 标签表），不要写死成固定枚举。
- 人 / 岗 / 项 三张视图：谁在做、在哪个项目、周期多长、该找谁 —— 由「在册 / 组织」对象承载。
- 业务域与人的边界由 human 决定；agent 只能**提案**，不能自己改权限。

## 失败模式

| 如果 | 那么 |
|---|---|
| 必填维度缺证据 | 留空并在 `00-brief.md` 标注缺哪一维、要补什么来源；**不要用通用常识填满** |
| 对象跨了两类 | 就近归类，写明为什么这样归，并标出越界的那部分 |
| 授权来源说不清（谁授的 / 范围多大 / 多久） | **停止蒸馏**，先把授权补上 |
| 多个来源互相冲突 | 保留冲突并定位，转 `needs_review`；不要挑一个当真相 |
| 同一对象已有旧产物 | 先合并旧产物，不平行再造一份 |

🔴 **CHECKPOINT**：授权来源未经 human 确认前，不进入提取。

## 反例黑名单（不要做）

- 不要用通用常识补齐没证据的维度。
- 不要把个人偏好写成部门 / 业务域规则。
- 不要在授权来源不清楚时开工。
- 不要把「只出现一次」的行为写成偏好。
- 不要替对象消解矛盾，不要替对方表态。
- 不要写死业务域枚举 —— 字段要可自定义。

## 注意

- 对象类型不匹配时就近归类，并在 `00-brief.md` 写明为什么这样归。
- 同一对象重复蒸时，先合并已有产物，不要平行造两份。
