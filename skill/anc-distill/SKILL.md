# 技能: anc-distill

## 使用方式

给一份原料 + 一个蒸馏目标，产出一组可安装的能力卡和一份可追溯审计。

```
/anc-distill <原料路径或来源> [对象类型]
```

## 功能描述

把「给人读的总结」变成「给 agent 执行的资产」。

这条路上最贵的失败不是做得少，是两个：

1. **做出来没人调用** —— trigger 写不准，能力存在却永不触发，或到处误触发；
2. **看着对但跑不动** —— 有观点没步骤，换一组输入就执行不下去。

本技能用「验证在前、数量在后」回避这两种失败：先把候选压到可核验的证据上，再决定谁值得成为独立入口；没晋级的**不删掉**，降级保留。

## 与兄弟技能的分工

| 你要做的事 | 用哪个 |
|---|---|
| 定「蒸馏什么对象、要哪些维度、授权怎么算」 | `anc-distill-targets` |
| 评「产物够不够好、怎么变强」 | `anc-evolve` |
| 从原料走到产物 | **本技能** |

## 不变量（任何一轮都不能违反）

1. **原子**：一个能力只做一个方法论单元，不写「大而全」。
2. **可追溯**：每个能力必须有可回查的原文位置（章节 / 页码 / 时间戳 / chunk id），不能只有来源名。
3. **可验证**：每个能力必须过三重验证 + 压力测试；纸面推演不等于实测。
4. **可进化**：每个晋级能力必须自带评测用例（格式随 `anc-evolve`）。
5. **人参与**：阶段 0 / 3 / 5 三处必须停下来等 human 确认。
6. **可交付**：终点是「装进 skills 目录能被调用」，不是「写完了」。
7. **单一事实源**：单入口版与域包版从同一份能力清单编译，不各写一份。

## 执行流程

产物目录（`<slug>` 为蒸馏对象短名）：

```
<工作目录>/<slug>/
├── 00-brief.md            骨架与范围（阶段 0）
├── 01-candidates/         候选池，每来源一个文件
├── 02-verify.md           三重验证记录 + 四类分流
├── 03-promote.md          晋级门记录 + 去向表
├── 04-cards/<cap-id>.md   能力卡（R/I/A1/A2/E/B 六段）
├── 05-links.md            引用关系 + 术语表
├── 06-pressure.md         压力测试记录（触发 + 真实输出）
├── 07-audit.md            覆盖审计：缺口 / 未验证 / 未采纳及理由
└── out/<skill-name>/      编译产物（可安装）
```

### 阶段 0 — 定范围（骨架）

输入：原料 + 对象类型 + 使用场景。

动作：读对象模板（见 `anc-distill-targets`），列出这份原料**能给什么**、**要它干什么**、**够不够**。

输出：`00-brief.md` —— 范围、对象类型、必填维度清单、预期的最终能力数量级。

🔴 **CHECKPOINT**：把骨架给 human 看。骨架错了后面全错，不要跳过。

**失败模式**：原料不足（缺必填维度的证据）→ 在 `00-brief.md` 写明缺哪几维、要补什么来源，**不要用通用知识把维度填满**。

### 阶段 1 — 整体理解

输入：原料。

动作：按「结构 → 解释 → 批判」三层读 —— ①它在讲什么结构；②每部分主张什么；③哪些是主张、哪些是证据、哪些是作者立场。

输出：写进 `00-brief.md` 的「关键任务清单」—— 这份原料**声称能解决**的问题列表（后面用它查覆盖率）。

### 阶段 2 — 多源并行提取

输入：原料切块。

动作：默认 6 路提取器并行，各自独立产出候选，**禁止互相参考**：

| 路 | 抓什么 |
|---|---|
| 1 主张 | 论点、框架、原则 |
| 2 对话 | 立场变化、被追问时的回答 |
| 3 表达 | 高频词、专属术语、句式习惯 |
| 4 他者 | 外部评价、批评、反驳 |
| 5 决策 | 具体决策及其依据 |
| 6 时间线 | 顺序、演化、时效 |

输出：`01-candidates/<来源>-<n>.md`，每条含 `id / 一句话 / 类型 / 出处 / 证据原文`。

**降级**：环境不支持并行 → **串行跑同样 6 路 prompt**，产出格式不变。

**失败模式**：候选覆盖不全 → 对照阶段 1 的关键任务清单补扫；有未解释的遗漏就回头补，**不许报「零遗漏」**。

### 阶段 3 — 三重验证（知识验证）

对每条候选跑三关，**全过才算通过**：

| 关 | 问题 | 通过的样子 |
|---|---|---|
| V1 来源充分性 | 可定位的原文，够不够支撑这条在限定范围内的说法？ | 一处讲透即算通过；残缺公式 / 半条规则不算 |
| V2 可执行性 | 换一组**合法新输入**，能不能按它完成一个任务并核对结果？ | 新输入走一遍步骤 / 分支 / 输出 / 判停，有独立核对点 |
| V3 任务增益 | 固化这条，具体省了什么？ | 能说出可检查的收益：少遗漏 / 统一口径 / 稳定格式 / 识别失败边界 |

四类分流：

| 判定 | 条件 | 去向 |
|---|---|---|
| `verified` | 三关全过 | 进阶段 4 |
| `reference` | 有来源价值但不可独立执行 | 进术语表 / 参考区，登记实际落点 |
| `needs_review` | 关键条件缺失或来源冲突 | 列出具体缺口，**不进能力池** |
| `rejected` | 无原文依据 / 归因错误 / 被另一条完整覆盖 | 记理由 + 被谁覆盖 |

输出：`02-verify.md`（逐条记录三关结果与依据）。

**红线**：V2 的推演记为 `walkthrough`，**不等于**实测；**不许补造原料里没有的规则**；重要缺口不能静默消失。

🔴 **CHECKPOINT**：展示四类清单 + 重要缺口，等 human 确认入选名单。

### 阶段 4 — 晋级门（产品化验证）

知识验证通过 ≠ 值得成为**独立入口**。五条判据，前三条必须通过，后两条至少过一条：

| # | 判据 | 问法 |
|---|---|---|
| 1 | 独立意图 | 用户会不提来源、单独提这件事吗？ |
| 2 | 独立契约 | 有自己的输入 / 步骤 / 输出 / 完成标准，不只是观点或术语？ |
| 3 | 独立运行 | 不加载别的兄弟能力也能正确执行？ |
| 4 | 独立复用 | 会在多任务里重复调用，或需要被别的能力组合？ |
| 5 | 独立评测 | 能写出正向 / 负向 / 近邻 / 输出断言四类用例？ |

输出：`03-promote.md` 去向表 —— 每条 `promoted`（成为独立入口）或 `router`（保留为能力卡，经来源入口访问）。

**预算**：可发现入口软预算 **8** 个（含 1 个来源路由入口）。超了按调用频率 / 复用处 / 独特性 / 证据强度 / 触发可分性排序，超出的降为能力卡。

**硬规则**：未晋级的**不进 rejected**（它过了知识验证，只是不单独发现）；把输出契约不同的能力硬拼成一个模糊入口是禁止的。

### 阶段 5 — 构造能力卡

每条通过的能力写一张卡，六段齐全：

| 段 | 内容 |
|---|---|
| R | 原文依据（引用 ≤150 字/段，英文 ≤100 词/段），逐项对应到规则 |
| I | 用自己的话重述（禁止原句搬运） |
| A1 | 来源案例；无案例时如实标注，合成演练**不得冒充**原文事实 |
| A2 | 触发与适用：什么时候该用它、什么**不该**用它（近邻负例） |
| E | 可执行步骤：输入 / 步骤 / 分支 / 判停 / 完成标准 |
| B | 边界与反例：前提、失效条件、作者立场、时效 |

输出：`04-cards/<cap-id>.md`（正文不带 frontmatter，元数据另记）。

### 阶段 6 — 链接

动作：①找出能力间引用关系，写进各卡的 `also_read`；②整理术语表到 `05-links.md`；③在 A2 回填「与相邻能力怎么区分」。

**目的**：让路由表能自动生成，且相邻能力互有负例、不双触发。

### 阶段 7 — 压力测试

晋级能力**测触发**，router 能力**测可达**。两类都要**真的做完一个代表任务并核对输出**。

```
每个能力：
  1. 触发测试：正向 prompt 该触发吗？负向 prompt 该不触发吗？近邻 prompt 会不会撞车？
  2. 执行测试：跑一个代表任务，核对输出是否达到 E 段的完成标准
  3. 基线对照：同一个 prompt 不带该能力跑一遍，比质量
```

输出：`06-pressure.md`。**缺失输出计入评测分母，未完成不得写「通过」**。没过的回阶段 5 重做。

**失败模式**：环境跑不了真执行 → 干跑推演并**标 `dry_run`**；干跑占比过高按 `anc-evolve` 的失效阈值处理。

### 阶段 8 — 编译与交付

1. 生成 `out/<skill-name>/SKILL.md`（单入口版）或域包版 —— **两份从同一份能力清单编译**；
2. 校验：frontmatter 100% 合规、相对引用路径可达；
3. 把编译产物装到 skills 目录，或按 human 指定的位置；
4. 写 `07-audit.md` 收尾：覆盖率、缺口、未验证项、未采纳项及理由。

🔴 **CHECKPOINT**：编译前确认输出模式（单一入口 / 域包）与安装位置。

## 反例黑名单（不要做）

- 不要为了凑数量把弱能力包装成独立 skill；宁少勿多。
- 不要用「一处提到」当充分证据，也不要用「只出现一次」一票否决。
- 不要用通用常识补齐原料缺失的维度。
- 不要把纸面推演说成实测，不要把 `dry_run` 说成跑过。
- 不要静默丢弃未晋级 / 待核查内容。
- 不要跳过三个阶段中的任一 CHECKPOINT。
- 不要在这里设计「业务门禁」（准入 / 审批规则）—— 那是被蒸馏对象的内容，不是本技能的产物。
