# 技能: anc-evolve

## 使用方式

输入一组已存在的 skill / 能力卡，产出评分 + 具体改动 + 留痕记录。

```
/anc-evolve <skill 目录或域包> [--only-score]
```

## 功能描述

「沉淀」不是终点，资产会腐化：环境变了、trigger 不准了、写的时候自以为是。

本技能把评测做成**可重复的循环**，并且明确区分两种判定：

- **排序**（先改谁）—— 可以用绝对分；
- **留还是回退**（改得好不好）—— **不能用绝对分**。

为什么：LLM judge 给的是抽样，不是测量。同一份**没改过**的文字换个 judge 评，总分能摆 ±8。
所以 keep / revert 一律走「同一个 judge 在同一轮里比两版」的成对比较 —— 两版共享同一把不准的尺，噪音在比较中抵销。

## 评分卡（9 维 / 100 分）

### 结构维（59）—— 静态可查

| # | 维度 | 权重 | 判什么 |
|---|---|---|---|
| 1 | Frontmatter | 7 | name 规范、description 含触发词、≤1024 字符；结尾不许有「灵活应用」类空话 |
| 2 | 工作流清晰度 | 12 | 有步骤、有序号、每步有输入 / 输出 |
| 3 | 失败模式编码 | 12 | **必须写出「如果 X 失败 → Y」**；只有正向流程扣 ≥3 |
| 4 | 检查点设计 | 6 | 关键决策前有 human 确认；检查点要显式标记（🔴 / STOP），「建议…」不算 |
| 5 | 可执行具体性 | 18 | 有具体参数 / 格式 / 示例；「建议 / 可以考虑 / 视情况」出现 ≥3 处扣 ≥3 |
| 6 | 资源整合 | 4 | references / scripts 引用可达 |

### 效果维（35）—— 必须实测

| # | 维度 | 权重 | 判什么 |
|---|---|---|---|
| 7 | 整体架构 | 12 | 不冗余不遗漏；AI 腔废话（「说白了 / 换句话说 / 首先其次综上」）一处扣 1 |
| 8 | 实测表现 | 23 | 带 skill 跑 vs 不带跑，输出质量差多少；有没有引入副作用 |

### Meta 维（6）

| # | 维度 | 权重 | 判什么 |
|---|---|---|---|
| 9 | 反例与黑名单 | 6 | 必须有「不要做什么」清单；只写应做不写禁区扣 ≥3 |

计分：维度 1–7、9 各打 1–10 分 × 权重；维度 8 跑 2–3 个 prompt 打 1–10。

**总分 = Σ(维度分 × 权重) / 10**

## 闸门项（独立于评分，命中必须先修）

| 闸门 | 判据 |
|---|---|
| 运行时中立 | 是否绑死某个 harness 的命令 / 路径 / 目录名？绑了就必须先改成形态描述（入口 / 落点 / 句柄），否则换 harness 就失效 |
| 单一事实源 | 同一份内容是否被抄成两处？抄了就先合成一处 |

**为什么单列**：这两项是「换环境就死」，不是「分数低一点」。

## 阶段 A：基线（只用于排序）

```
每个 skill：
  1. 读全文，按维度 1–7、9 打分（附一句理由）
  2. 每个测试 prompt 跑两遍（带 / 不带），打维度 8
  3. 记 results.tsv，输出评分卡，按总分从低到高排
```

🔴 **CHECKPOINT**：评分卡给 human 看，确认后再进循环。

排序只看绝对分 —— 它决定「先改谁」，**不决定 keep / revert**。

## 阶段 B：优化循环

```
round = 0
while round < 3:
    1. 找加权短板：weighted_gap = 权重 × (10 − 维度分) / 10
       —— 不用「原始分最低」：低权重维度会制造进步幻觉
       —— 相关簇警告：维度 2 / 3 / 4 通常一起动，别单修一个就当完成
    2. 提方案：改哪一段、对应哪条评分、预期涨多少
    3. 改文件 + 留痕（版本号 + 改动摘要）
    4. 成对复评：同一 judge 在一次比较里读两版（改前 / 改后），
       按评分卡当比较准则，回 {更好 | 更差 | 持平} + {明显 | 轻微}
       N = 3（奇数；接近时升到 5）
    5. 多数决：更好 ≥ 更差 → 留；否则回退
```

回退也要留痕（记 `results.tsv`，标 `revert`）—— 回退是数据，不是失败。

## test-prompts.json（每个 skill 必带）

```json
[
  {"id": 1, "prompt": "用户真会说的话", "expected": "期望输出的简短描述"},
  {"id": 2, "prompt": "稍复杂或有歧义的场景", "expected": "期望输出"}
]
```

规则：**典型场景优先，不是边缘 case**；写完先给 human 看，确认再评。测试 prompt 的质量决定优化方向对不对。

## results.tsv 字段

| 字段 | 说明 |
|---|---|
| `ts` | 时间 |
| `skill` | 名字 |
| `round` | 第几轮 |
| `mode` | `baseline` / `optimize` / `revert` |
| `dim` | 本轮针对的维度 |
| `score_before` / `score_after` | 绝对分（仅参考） |
| `verdict` | `better` / `worse` / `tie` |
| `judges` | 投票分布，如 `2-1` |
| `dry_run` | `true` / `false` |
| `note` | 一句话 |

## 失败模式

| 如果 | 那么 |
|---|---|
| 子 agent 不可用（超时 / 限流） | 退化干跑推演，**必须标 `dry_run`**；不要跳过维度 8 |
| `dry_run` 占比 > 30% | **评估失效警告**，结论不得用于决策 |
| 同一 judge 前后绝对分差在 ±8 以内 | 视为噪音，不得据此 keep / revert，改走成对比较 |
| 三个 judge 分裂（1-1-1） | 加到 5 个；仍分裂 → 交 human 判 |
| 改动只碰了措辞 | 大概率落在噪音带里，先问值不值得改 |

## 反例黑名单（本技能自己不要做的事）

- 不要用绝对分决定 keep / revert。
- 不要为了提高分数往文里塞 🔴 标记或加长废话。
- 不要改一处就宣称提升，必须成对比较。
- 不要跳过维度 8 然后声称已评测。
- 不要一次改多个维度，导致无法归因。
- 不要在 human 未确认基线时进入优化循环。

## 与 ANC 的接法

- 定期迭代（周 / 月）就是本技能的循环；结果沉淀在 `results.tsv` + 版本记录里。
- `anc-distill` 阶段 7 的压力测试用本技能的 `test-prompts.json` 格式，保持兼容。
- 评测结论只用于**排序与取舍**；涉及权限 / 口径的改动仍由 human 决定。
