# ADR：前端为什么手搓，以及现在该不该换框架

2026-11-15。回答「你为什么前端用手搓而不是用框架」。

## 一、当时的理由（现在看，哪几条还成立）

| 理由 | 当时成立吗 | 现在还成立吗 |
|---|---|---|
| 页面少（3–4 页）、数据全是服务端给的 JSON，没有复杂本地状态 | ✅ | ❌ **已经 9 页 + 审批/结账/签发这些有状态的写流程** |
| 不想为了装框架引入构建链（当时只有 Go + esbuild） | ✅ | ✅ 但这条其实不构成阻碍：esbuild 本来就在，打包 React/Vue 也是同一个 esbuild |
| 单二进制、`go:embed` 前端产物 | ✅ | ✅ 这条与框架**不冲突**：框架产物也是一个 `app.js` |
| 零第三方依赖（Go 侧的红线）被顺手延伸到了前端 | ⚠️ 延伸过度 | ❌ 后端零依赖是为了交付物；前端产物本来就是编译结果，不需要"零依赖" |

**最重要的一条我当时没写下来：手搓意味着自己实现"重绘"。** 而重绘恰恰是框架的核心价值。

## 二、手搓的实际代价（这几周出现的每一个问题都在这个清单里）

| 症状 | 根因 |
|---|---|
| 轮询后整页跳一下、滚动丢失 | 没有 diff/生命周期 → 只能整棵重建 |
| 拖宽侧栏点一下弹回去 | 没有组件状态 → 宽度存在 DOM 上，重建即丢 |
| 17 处错误态只有 2 处有"重试" | 没有统一的错误组件 → 每处手写，漏是必然 |
| 七份 CSS 互相覆盖、16 处 `!important` | 没有作用域样式 → 全局命名空间打架 |
| 表格排序/分页/虚拟滚动做不出来 | 没有生态 → 每个都要手写，手写就不做 |
| 抽屉状态不进 URL、Esc 不关 | 没有路由/焦点管理 |

**这些不是"还没做"，是"手搓这种形态下做起来极贵"。**

## 三、框架能换来什么（只列我们真正需要的）

- **组件生命周期与 keyed 更新** → 刷新不再重建，滚动/焦点/输入不丢（我们手写了 `quietRefresh` 去补这个洞）
- **作用域样式**（Vue SFC 的 `scoped`）→ 告别 `!important` 收口
- **生态**：表格（TanStack Table）、虚拟滚动、图表、日期、表单校验 —— 这些我们一个都没有
- **测试工具**（Testing Library / Vitest）→ 现在只能靠 ego-browser 端到端点点点

## 四、代价

| 项 | 量 |
|---|---|
| 重写范围 | 页面层（9 页 + 若干子标签），约 5–6k 行 TS；`api.ts` / `types.ts` / 契约校验**可以原样保留** |
| 新增依赖 | Vue 3 运行时 ~34KB gz（含编译器则更大；用 SFC 预编译只带 runtime） |
| 构建 | 仍是 esbuild（配 `vue` 的 esbuild 插件）或换成 Vite；产物仍 `go:embed` |
| 交付物 | **仍是单二进制**，这条不变 |

## 五、我的建议

**换 Vue 3 + TypeScript，只换表现层。**

理由：
1. 我们已经有 TS 类型与契约校验，Vue 的 SFC + `lang="ts"` 直接吃这些；
2. 交付物形态不变（单二进制），部署故事不动；
3. 我们踩的每一个坑都正好是框架解决的那一类（重绘、状态、样式作用域、生态）。

**不换 React 的理由**：SFC 的 `scoped` 样式与 `template` 更接近我们现在的"一页一个 render 函数"结构，迁移映射最直接；React 的生态更大，但我们短期用不到。

**迁移顺序（避免大爆炸）**：
1. 先搭一层壳：Vue 应用 + 现有 `api.ts`/`types.ts` 原样接入，只做"取数与顶栏/侧栏";
2. 一页一页搬，每搬完一页跑一遍 `dev/dev.sh ui`（不变量检查）+ `dev.sh types`（契约检查）；
3. 全部搬完再删手搓的 `el()` 层与七份 CSS。

**风险**：这是一次真正的重写，不是重构。按现在的速度，9 页大约需要 3–5 轮完整会话。
在此之前，**手搓这版就是"能用的证据"**，不该再往里加新功能。

## 六、一句话

手搓不是错在"没上框架"，是错在**没有在页数从 3 变 9 时重新做这个决定**。
现在做，比等到 20 页再做便宜。

# 附：为什么候选是这几个、以及一个便宜的先验

## 一、先分清两件事

选型被混在一起讨论过：**视图层框架** 与 **组件库**。
我们真正缺的是后者——表格（排序/分页/固定列）、抽屉、表单校验、可访问性，
这些手搓成本极高，而且我们已经用"完全不写"的方式回避了它们。

| 层 | 候选 | 对我们的影响 |
|---|---|---|
| 视图层 | 手搓 / Vue 3 / React / Svelte 5 / Lit | 决定"重绘与状态"这一层 |
| 组件库 | Naive UI / Element Plus（Vue）· Ant Design / shadcn（React）· 无（手搓） | **决定表格/抽屉/表单能不能立刻有** |

## 二、五个候选，按我们的约束打分

约束：单二进制 + `go:embed`、本地部署、数据密集、长期内部工具、文档要中文友好、
迁移成本（现有 `api.ts`/`types.ts` 要能直接复用）。

| 选项 | 重绘/状态 | 组件生态 | 迁移映射 | 中文生态 | 判断 |
|---|---|---|---|---|---|
| 继续手搓 + 加 TanStack Table | 自己写 | 弱（只有表格） | — | — | 只解决表格，其余七项照旧 |
| **Vue 3 + Naive UI** | ✅ | **强**（表格/抽屉/表单/日期齐全） | **高**（模板 ≈ 现在的 render 函数） | **最好** | **推荐** |
| React + Ant Design | ✅ | 最强 | 中（JSX + hooks 要重学一套心智） | 好 | 可选，但我们短期用不到它的规模 |
| Svelte 5 | ✅（无 VDOM，最省） | 中 | 中 | 弱 | 技术最优雅，生态最薄 |
| Lit / Web Components | ✅（标准） | 弱 | 中 | 弱 | 组件库这块等于要从零开始 |

**结论**：Vue 3 + Naive UI。不是因为 Vue 最好，而是**"迁移映射 + 中文组件库"这两项它同时占优**。

## 三、便宜的先验（先做一页，再决定）

按项目红线"重写必须说清收益"，不做全量押注。先做一个**可回退的实验**：

**用 Vue 3 + Naive UI 重做「审计」页**（我们最表格化、也最能体现差距的一页），验收四条：

1. 代码行数：手搓版 vs Vue 版（现在 `pages/audit.ts` 约 300 行 + 对应 CSS）
2. 是否自带排序/分页/固定列/空态/错误态（Naive 的 `n-data-table` 直接给）
3. `dev/dev.sh ui` 的 10 条不变量是否仍全绿
4. `dev/dev.sh types` 契约校验是否不受影响

**通过则继续搬第二页；不通过则保留手搓，只把 Naive 的表格思路借过来。**

代价：约一轮完整会话；风险可控（新增代码在独立目录，不删旧页）。

## 四、明确不做的

- 不做 SSR / 不做多页应用（我们是本地看板，不需要）
- 不引状态管理库（Pinia 等）：页面级状态够用，等真有跨页共享再加
- 不为换框架而换：如果实验不过，就停

# 修正：判据是「中英两种生态都强」，结论翻到 React

上面那张表把「中文生态」单独列了一列，等于默认了"中文好用优先"。
**这个判据是错的** —— 应当要求**中英两边都强**。按这条重打：

| | 英文生态 | 中文生态 | 合计 |
|---|---|---|---|
| **React** | **第一**（TanStack、Radix、shadcn、MUI、Recharts、Testing Library…） | **强**（Ant Design 中国出品、ahooks、umi，社区巨大） | **两边都第一梯队** |
| Vue | 第二（PrimeVue/Vuetify/Quasar，够用但不是首选） | 很强（Element Plus、Naive UI 中国出品） | 中文强、英文次一档 |
| Svelte | 中 | 弱 | 弱 |
| Lit | 弱 | 弱 | 弱 |

## 还有一条我上一轮低估的：JSX 与手搓的 `el()` 几乎是同构

现在的写法：

```ts
el("div", { class: "ledger-row" }, el("div", { class: "who" }, "待你签"), el("div", { class: "what" }, title))
```

换成 JSX：

```tsx
<div className="ledger-row">
  <div className="who">待你签</div>
  <div className="what">{title}</div>
</div>
```

**这是一次机械变换**，不是重新设计。Vue 的模板语法与程序化 `el()` 之间反而要绕一层
（`v-for`/`v-if` 对应到 `map`/三元，心智要换）。

## 修正后的推荐

**React 19 + TypeScript + Ant Design（表格/表单/抽屉/中文文案）+ 按需引入**。

- 交付形态不变：仍是 esbuild/vite 打包出一个 `app.js` → `go:embed` → 单二进制
- `api.ts` / `types.ts` / 契约校验 / 不变量检查全部原样保留
- 迁移方式：`el(...)` → JSX 机械替换，一页一页做，每页跑 `dev.sh ui` + `dev.sh types`

**实验不变、对象换了**：仍先做「审计页」，只是用 React + AntD 而不是 Vue + Naive。
验收四条不变（行数、是否自带排序分页固定列、不变量全绿、契约校验不受影响）。
