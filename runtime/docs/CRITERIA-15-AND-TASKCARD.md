# 判据 15 的口径 + 任务卡是不是伪需求

> 2026-11-19。两件事：**"最坏代价"到底怎么定口径**；以及**任务卡这件事我们是不是定死了、甚至做了个伪需求**。

---

## 一、判据 15：待批按"最坏代价"排序

### 1.1 它要解决什么

一线负责人的原话是：「20 条待批堆在我这，我要按**最坏损失**排序，不是按时间排序。」

所以这条判据的目标只有一个：**该先看哪一条**。它不要求我们算出精确损失 ——
那是判断，不是计算。

### 1.2 口径（建议）

`worst_case` 是**提案方声明的结构化字段**，不是我们推导的数字：

```yaml
worst_case:
  kind: 钱 | 承诺 | 数据 | 合规 | 时间
  amount: 50000          # 仅 kind=钱；单位为本币最小单位
  currency: CNY          # 仅 kind=钱
  reversible: false      # **不可逆**是最强的排序键
  basis: "合同第 3.2 条：逾期按日万分之五"   # 凭什么这么估
```

排序规则（写死，不可配 —— 同评分那条纪律）：

```
1. 不可逆的排前面
2. 同类里金额降序
3. 没有 worst_case 的排最后，但**标「未评估」**，不当作 0 混进去
```

### 1.3 为什么必须由提案方填

只有他知道这一单的规模：金额在合同里、承诺在 SOW 里、数据范围在清单里。
**让审批人自己填等于让他先干一遍活**，那还不如按时间排。

### 1.4 允许默认值，但必须标出来

域表里可以给一个默认（例如"大宗贸易的单笔均值"），但看板要显示
`金额 5 万（按域默认值，未核实）` —— **默认值不许冒充声明值**。

### 1.5 这条判据的验收（可执行）

| 场景 | 期望 |
|---|---|
| 三条待批：50 万不可逆 / 5 千可逆 / 未填 | 按 50 万 → 5 千 → 未填 排序，未填那条显示「未评估」 |
| 全部未填 | 退回按时间排序，并在页头说明「本队列没有代价信息」 |
| 只有金额没有 basis | 显示但标「无依据」 |

### 1.6 诚实边界

- **算不出来的是什么**：承诺类、合规类的"最坏"是判断，不是计算；我们能做的是**要求写依据**，不是替他想。
- **可造假**：提案方可能故意写小金额。缓解：`basis` 必须指到原文（合同/SOW 的行号），审计能回查。
- **它不解决"该不该批"**：排序只决定先看哪条，不替代判断。

## 二、任务卡：一个我可能造出来的伪需求

### 2.1 它是怎么来的

时间线：用户说「一个文科职员能不能看懂你给他下发的任务」→ 我在治理文档里写了一张"人机分工卡"样例 →
后来把它写成了判据 10（人能看懂自己的任务）与判据 11（边界明确）。

**注意这一步跳跃**：「要让人看懂」是一个**真实需求**；
「所以要有一张每任务一张、带版本号、带维护人的卡片」是一个**我自己加出来的产物**。

### 2.2 三条反证：它站不住

1. **没有生产者**：卡片是手写的。谁写？提案的 bot 不会写，看板不会生成，人也不愿意每单写一张。
2. **版本号是伪治理**：`卡片版本 3 · 2026-11-20 起用 · 维护人：李默` —— 给一个没人维护的产物加版本，
   只是把负担换了个名字。**这正是我们批过的"用治理动作掩盖没有产品"**。
3. **判据 10 的验收测的是人，不是产物**：它写的是"非技术同事能复述"，
   那是一次**可用性测试**，不需要一张独立文档 —— 只要页面本身能回答那五问。

### 2.3 结论：需求留下，产物砍掉

| 保留 | 砍掉 |
|---|---|
| 「一个非技术的人，看完能回答：我要做什么 / Agent 做什么 / 我不能做什么 / 卡住找谁 / 错了怎么办」 | 独立的任务卡文件、版本号、维护人 |
| 判定树（谁拍板）要能被 5 个人答出同一套 | "每张卡三行以内"这种形式规定 |

### 2.4 替代方案（三件东西，都不是新产物）

| 做法 | 落在哪 | 为什么比卡片好 |
|---|---|---|
| **待批/任务页渲染"五问"** | 看板页头，从 `Pending` / `task` 字段直接渲染 | 有数据就自动有；没有数据的格子空着并说明缺什么 → **反过来暴露数据缺口** |
| **岗位说明书一页**（role 级，不是 task 级） | `roles/<role>/README.md` | 一页管一类活；不需要每单维护 |
| **判定树做成可执行分类器** | `anc division --case "..."` + 20 题答案集 | 边界靠"答案一致率"验，不靠人读一段话 |

### 2.5 判据改写（原来的 10/11 作废）

| 新判据 | 验法 | 过的标准 |
|---|---|---|
| **10' 页面自解释** | 取 3 个真实任务页，让 3 名非技术同事各答 5 问 | 3/3 全对；错题原文回填到页面缺什么 |
| **11' 边界可执行** | 20 道带标准答案的案例跑 `anc division` | 与人工答案一致率 ≥ 95%；分歧题逐条改规则 |

**共同点**：都不需要新文档，只需要把已有页面的字段补全、把判定树变成能跑的东西。

## 三、这件事的教训（写下来）

**我把"测试"误当成了"产物"。**
判据 10 本来是一次可用性测试（人能不能看懂），我在落地时把它变成了一个需要有生产者的对象（卡片）。
判据一旦要求一个**没有生产者的产物**，它就会在三个月内变成一份过期的手写文档 ——
而那正是这个产品最反对的东西。

以后写判据前先问一句：**谁生产它？谁维护它？** 答不上来，就说明它不该存在。
