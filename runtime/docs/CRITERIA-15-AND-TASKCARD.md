# 判据 15 的口径 + 任务卡是不是伪需求

> 2026-11-19。两件事：**"最坏代价"到底怎么定口径**；以及**任务卡这件事我们是不是定死了、甚至做了个伪需求**。

---

## 一、判据 15：**这一条我们定错了归属**

### 1.1 我原来的方案，越界了

我写的是：给提案加 `worst_case` 结构字段（kind/amount/reversible/basis），
再在 ANC 里写死一条排序规则「不可逆优先 → 金额降序 → 未填最后」。

**用户指出这是错的，而且错在归属：**

> ANC 是做信息流转、组织调配的中枢神经系统，不是子 Agent 要干的活。
> 这种判断要交给一线负责人——**他手上的 Agent** 去向 ANC 读取上下文，
> 再由那个 Agent 去决定字段与顺序。

也就是说：**"最坏代价是多少、该先看哪条"是业务判断，属于一线那个懂业务的 Agent；
ANC 只该保证它读得到、读得全、读得出处。**

### 1.2 为什么也不该用规则框死

- **业务在变**：今天按金额、明天按合规、下个月按客户等级 —— 在代码里写死就是写死一个过期的判断。
- **人在变**：同一个负责人换了打法，规则不会跟着换。
- **prompt 的约束面积也有限**：一句"请按最坏损失排序"给不出领域知识；
  真正管用的是**一个用了很久、懂这个人和这摊事的 agent**（例如长期记忆型的 Hermes 那类），而不是一段提示词。

### 1.3 修正后：ANC 的责任边界

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| **ANC** | 把事情**端到该看的人面前**：队列、上下文、依据、出处、历史；字段**可空、可自由描述**；缺什么显式标出 | 不判断哪条更重、不排序、不替业务定义"最坏" |
| **一线 Agent** | 读 ANC 的队列与上下文，结合它对人和业务的长期理解，**决定怎么看、按什么排** | 不自己造事实，不绕过授权与审计 |

### 1.4 判据 15 改写为：**外部可判读性**（15'）

原来的判据是"待批按最坏代价排序"——测的是 ANC 里的一个算法。
改成测**ANC 交给下游的料够不够判**：

> 给定 20 条真实待批，一个**只通过 ANC 接口**（队列 + 上下文 + 时间线）
> 的外部 agent，能否为它们排出优先级，并与一线负责人的判断达到可接受的一致率。

| 项 | 内容 |
|---|---|
| 样本 | 20 条真实待批（含标题/正文/refs/域/项目/进队时间） |
| 判法 | 外部 agent 只看 ANC 给的料 → 排序 → 与人工排序比对 |
| 过 | 一致率 ≥ 约定的阈值；**不一致的条目逐条看：是 ANC 缺料，还是 agent 判断不同** |
| 意义 | 不达标说明**我们端上去的料不够**（缺字段、缺历史、缺出处），而不是"agent 笨" |

这条判据的好处：它把责任放对了 ——
**ANC 只对"信息是否充分可判"负责，不对"判断是否高明"负责。**

### 1.5 那 `worst_case` 字段还要不要

**不要作为必填 schema。** 但两件事可以留：

1. 提案的 `refs` / `body` 里**允许自由描述代价**（合同条款、金额、客户等级）——ANC 原样搬运，不解析。
2. 队列页**显示每条缺什么**（没有 refs、没有 body、没有域）——这是"料够不够"的体检，与排序无关。

## 二、任务卡：一个我可能造出来的伪需求

### 2.1 它是怎么来的

时间线：用户说「一个文科职员能不能看懂你给他下发的任务」→ 我在治理文档里写了一张"人机分工卡"样例 →
后来把它写成了判据 10（人能看懂自己的任务）与判据 11（边界明确）。

**注意这一步跳跃**：「要让人看懂」是一个**真实需求**；
「所以要有一张每任务一张、带版本号、带维护人的卡片」是一个**我自己加出来的产物**。

### 2.2 三条反证：它站不住

1. **没有生产者**：卡片是手写的。谁写？提案的 bot 不会写，看板不会生成，人也不愿意每单写一张。
2. **版本号是伪治理**：`卡片版本 3 · 2026-11-20 起用 · 维护人：李默` —— 给一个没人维护的产物加版本，
   只是把负担换了个名字。**这正是我们批过的"用治理动作掩盖没有产品"**。
3. **判据 10 的验收测的是人，不是产物**：它写的是"非技术同事能复述"，
   那是一次**可用性测试**，不需要一张独立文档 —— 只要页面本身能回答那五问。

### 2.3 结论：需求留下，产物砍掉

| 保留 | 砍掉 |
|---|---|
| 「一个非技术的人，看完能回答：我要做什么 / Agent 做什么 / 我不能做什么 / 卡住找谁 / 错了怎么办」 | 独立的任务卡文件、版本号、维护人 |
| 判定树（谁拍板）要能被 5 个人答出同一套 | "每张卡三行以内"这种形式规定 |

### 2.4 替代方案（三件东西，都不是新产物）

| 做法 | 落在哪 | 为什么比卡片好 |
|---|---|---|
| **待批/任务页渲染"五问"** | 看板页头，从 `Pending` / `task` 字段直接渲染 | 有数据就自动有；没有数据的格子空着并说明缺什么 → **反过来暴露数据缺口** |
| **岗位说明书一页**（role 级，不是 task 级） | `roles/<role>/README.md` | 一页管一类活；不需要每单维护 |
| **判定树做成可执行分类器** | `anc division --case "..."` + 20 题答案集 | 边界靠"答案一致率"验，不靠人读一段话 |

### 2.5 判据改写（原来的 10/11 作废）

| 新判据 | 验法 | 过的标准 |
|---|---|---|
| **10' 页面自解释** | 取 3 个真实任务页，让 3 名非技术同事各答 5 问 | 3/3 全对；错题原文回填到页面缺什么 |
| **11' 边界可执行** | 20 道带标准答案的案例跑 `anc division` | 与人工答案一致率 ≥ 95%；分歧题逐条改规则 |

**共同点**：都不需要新文档，只需要把已有页面的字段补全、把判定树变成能跑的东西。

## 三、这件事的教训（写下来）

**我把"测试"误当成了"产物"。**
判据 10 本来是一次可用性测试（人能不能看懂），我在落地时把它变成了一个需要有生产者的对象（卡片）。
判据一旦要求一个**没有生产者的产物**，它就会在三个月内变成一份过期的手写文档 ——
而那正是这个产品最反对的东西。

以后写判据前先问一句：**谁生产它？谁维护它？** 答不上来，就说明它不该存在。

## 四、15' 实测（2026-11-20）：一个只读接口的 agent 能不能排？

**做法**：给一个 agent 三个只读接口（`/api/approvals`、`/api/timeline`、`/api/board`），20 条真实待批，
要求它排序并说明"缺什么料"。

**结论：排不出来。** 它只排出了两件事：哪 4 条接口自己说了"不知道该谁批"、哪 1 条正文自述"无法回滚"。
第 8 名往后基本是"谁把话说清楚了"的序，不是业务重要性序。

### 四个根因（都是 ANC 端的料不够）

| # | 问题 | 证据 |
|---|---|---|
| 1 | **`title` 是系统拼的**，不是提案人写的一句话 | 20 条只落在 5 个字面值上（`alice 申请 trade 的权` 等）；7 条字面完全相同，只能靠 body 区分 |
| 2 | **`brief` 是模板拼的** | `must_not` 与 `if_wrong` 20 条一字不差（都来自 `policy:approvals`）；只有 `escalate_to` 与 4 条 `missing` 有区分度 |
| 3 | **没有结构化金额 / 影响面 / 可逆性 / 截止** | 20 条里只有 3 条正文写了钱；可逆性只有 q17 自己写了"无法回滚"，删文件/删目录/停作业都没写 |
| 4 | **历史对不上** | timeline 10 个 case 与队列 0 对应；3 条审批收场全是"同意"，没有驳回可参照 |

### 它明确说"判不出"的还有

- `to: "manager"` 是角色，落不到人：alice/bob 同 role、同域、都无上级 → 该谁批判不出
- `project` 20 条全空；唯一项目 `trade-q3` 周期是 Q3，而入队时间已是 11 月
- 依据材料挂不上：正文提到"合同第 3.2 条""已比价"，但 approvals 条目没有 `refs`/attachments（timeline 有 `refs`，approvals 没有）

### 一条要澄清的（别冤枉系统）

20 条 `enqueued` 完全相同**是我造数据造成的**（同一个 `ts` 批量灌入），不是系统缺陷。
真环境下它会有区分度 —— 这条不能写进产品结论。

### 根因 4 的处理：先例查询（2026-11-20 已落）

`/api/precedents?domain=<域>&q=<关键词>` —— 只返回 `kind=decision` 的历史决策，
每条给：对应提案 id、结论词（同意/驳回/挂起）、谁批的、什么时候、标题与详情原文、refs。

三条纪律：
- 不做相似度打分、不排"最相关"——**哪条算同类由读的 agent 判断**（判据 15 的教训）
- 空结果明说"没查到先例"，不拿相近的凑数
- 关键词只在标题/详情原文里找，不做同义扩展

实测（demo vault）：`?domain=trade` 返回 3 条，全是 `同意`，且时间从新到旧 ——
这恰好暴露了另一个真相：**这个组织还没驳回过任何事**，所以"驳回的先例"查不到。
那不是接口的问题，是数据的问题，页面/接口都照实说。

### 下一步（按性价比）

1. **提案人写的一句话标题**：envelope 加 `title`，`Pending.Title` 用它，没有才退回合成值
2. **approvals 带 `refs`**：与 timeline 对齐，让"依据材料"挂得上
3. **`to` 落不到人**：`to: manager` 要能解析到具体成员（域表 + 成员表已经在，缺"这次该谁"的规则）
4. 结构化的金额/可逆性：**不作为 ANC 的必填 schema**（D20 的教训），但可以要求提案人**在正文里显著写**，并在 `brief` 里回指

## 五、15' 第二次实测（2026-11-20，料补过一遍）

补了 title / refs / precedents / stale 之后，用同一套 20 条数据再跑一次。

**结论：从「0 条可判」变成「6 条可判」（约三成），但整条队列仍排不出可靠先后。**

### 分界在第 7 名

- **1–6 名有依据**：金额可比（200 万/年 > 48 万/年 > 12 万 > 8 万）或明写不可逆（"无法回滚""不可恢复"）
- **7 名往后**：只剩"对象 + 一句定性 + 等了多久"，三者不能互相换算，agent 明说"这部分我不认"

### 四个根因的实际解决度

| 根因 | 判定 | 证据 |
|---|---|---|
| title 系统拼的 | **一半** | 20 条 title 各不相同、可定位；但接口里**没有"谁写的"字段**，agent 无法证实"这是提案人写的" |
| brief 模板 | **没解决** | `agent_does`/`must_not`/`if_wrong` 20 条逐字相同；只有 `from` 与 4 条 `missing` 有增量 |
| 金额/可逆/截止 | **0 项完整** | 金额 4/20、可逆 3/20、**截止 0/20**（15 个键里没有 due/deadline） |
| 历史对不上 | **没解决** | 10 条 trade 拿到**同一组** 3 条先例（不是按条匹配）；且先例的 title 与 detail 说的不是一件事 |

### agent 给的三项"仍然阻止判断"的料

1. **截止时间**（20/20 缺）——`age_hours` 只回答"等了多久"，不回答"还有多久"
2. **可逆性 + 影响面的量级**（17/20 没写可逆）——"含客户真实数据"和"影响全域"不能放同一把尺子上
3. **能对得上的依据** —— 20/20 有 `refs`，但**打不开**；所以前 6 名的理由全是"提案人说"

### 已按第 3 条动手：`/api/ref`

新增只读端点 `/api/ref?path=<vault 内相对路径>#行范围`：
- 复用 `files.Read` 同一套规则（防穿越、不读软链、64KB 上限）
- 支持 `#12` 与 `#12-20` 锚点，正好对上 `refs` 里的写法
- 读不到 / 越界 / 二进制 → 都给一句人话，不倒字节
- 实测：缺文件说"路径不存在"；`../../etc/passwd` 被拒

**这一条不是为了好看**：它把"提案人说"变成"我能自己核"，是前 6 名从"信"变"验"的唯一途径。

### 截止时间已接线（2026-11-20）

agent 列的第 1 项已落：`envelope.due_at` → `Pending.DueAt` → `hot.State.DueAt` → `PendingView`，
API 现在给三个字段：

```json
"due_at": "2026-11-20T20:32:30+08:00",
"hours_left": 19,     // 负数 = 已逾期
"overdue": false
```

三条纪律：
- **它是提案人的事实，不是我们的判断**：中枢只搬运 `due_at`，不替业务定截止
- **没给就不猜**：`due_at` 为空时三个字段都不出现（不是 0、不是"未设置"）
- **它不等于优先级**：`hours_left` 只回答"还有多久"；哪条更该先看仍由读的人判断

实测：一条 20 小时后到期的提案 → `hours_left: 19`、`overdue` 不出现（未逾期）。

### 还剩两项

1. **影响面的量级**（"含客户真实数据"到底是几条）—— 按 D20 不做必填 schema，只能要求提案人写清楚
2. **能对得上的依据** —— `/api/ref` 已能打开；还差"提案人写的 refs 是否真的存在"这一层校验（现在只有打开时才知道）
