# 上下文与权限治理：飞轮怎么转

> 2026-11-19。回答一个问题：**接入进来的上下文、不同人与 Agent 的权限、每次决策/卡点/突破，怎么治理成一台能自己转的机器。**
> 本文分两半：前半是「专家怎么想、拿什么标准量我们」，后半是**可以直接拿去做长程任务的 prompt 与计划**。

---

## 零、先说清现在卡在哪（不解决这三条，飞轮转不起来）

| 卡点 | 现状 | 后果 |
|---|---|---|
| **上下文有装配、没治理** | `/api/context` 能给出"某 agent 拿到什么"，但答不出"为什么是这些、被挡了什么、花了多少" | 无法调优，也无法向客户解释 |
| **权限有两层、没打通** | 岗位能力（`capabilities.md`）与跨域委派（`grants/`）各自判，**一个人/Agent 的"总权限"没有单一视图** | 客户问"这个 bot 到底能碰什么"，我们只能翻两个文件 |
| **经验有流水、没沉淀** | timeline/audit 记了每次决策、卡点、结果；但**没有一条从"事件"到"可复用经验"的通路** | 同一个坑会被踩第二次；skill 靠人挑，不靠证据 |

## 一、治理专家怎么想（以及他们会用什么）

### 1.1 四种典型思路

| 流派 | 核心问题 | 对我们的意义 |
|---|---|---|
| **DMBOK 2.0**（数据管理知识体系） | 谁拥有、谁负责、按什么标准、怎么度量 | 给出**角色语言**：Owner / Steward / Custodian；治理不是"IT 的事" |
| **盘·规·治·管·用**（国内落地路径） | 先盘清有什么，再定标准，再治质量，再管资产与安全，最后才谈用 | 我们的顺序错了：先做"用"（看板），后补"盘"与"规" |
| **数据契约 / Data Mesh** | 生产方与消费方之间要有可验证的契约 | 我们的"契约"是 `writeJSON` 的 payload —— 已经比口头约定强，但**没有版本与破坏性变更检查** |
| **AI 治理（NIST AI RMF / ISO 42001）** | 可问责、人类监督、记录留存、影响评估 | 我们的 audit 已经在做"记录"，缺"人类监督的证据"与"按角色而非按人归因" |

### 1.2 一条反直觉但关键的第三方标准

IETF 的 AI 治理记录草案（[draft-reilly-aigov](https://datatracker.ietf.org/doc/draft-reilly-aigov/)）里有一条硬规矩：

> **记录不得把 AI 使用归因到可识别的个人；`accountable_role` 必须写角色而不是人名。**

这条对我们的「按人记流水」是直接挑战：**看板能按人查，但账本本身应当按角色归因。**
处理办法：账本记 `actor`（谁）+ `role`（什么岗位，必填）+ `on_behalf_of`（代谁），
按人检索是**视图**，不是存储事实。这样既满足审计，也不把员工变成监控对象。

### 1.3 他们会用什么工具（我们不需要全上，但要知道对标物）

| 层 | 工具 | 我们用什么替代 |
|---|---|---|
| 元数据与血缘 | Apache Atlas / OpenMetadata / DataHub | `timeline.src` + `audit.src`（文件:行号）+ 本文的"血缘字段" |
| 血缘标准 | [OpenLineage](https://openlineage.io/) / [W3C PROV](https://www.w3.org/TR/prov-overview/) | 事件里带 `derived_from[]`；导出时按 PROV 映射 |
| 质量与契约 | Great Expectations / dbt tests | `dev/dev.sh types`（契约漂移）+ 规则表（已有） |
| 资产目录与分级 | Collibra / 阿里 DataWorks | `domains.md` + 数据源分级（已有雏形） |
| 权限与委派 | OPA / Cedar / Zanzibar 风格关系 | `capabilities.md` + `grants/` + `org.Exercise`（已是同一思路） |
| 度量 | 治理成熟度模型 L1–L5 | 本文第六节的"可检验判据" |

**共性**：他们没有一个是"再做一个看板"，全部是**先定对象与字段，再定谁能改、改了留什么痕**。
这正是我们下一步要做的事，而不是再加页面。

## 二、治理对象：五类，缺一不可

飞轮转的是这五类东西。每一类都要有：**标识、字段、权属、生命周期、留痕**。

| 对象 | 是什么 | 关键字段 | 谁能写 | 保留 |
|---|---|---|---|---|
| **C 上下文**（Context Pack） | 给某个主体（人/Agent）装配的一次上下文 | who, sections[], chars, why, version, derived_from[] | 装配器（自动） | 每次装配留摘要 30 天 |
| **D 决策**（Decision） | 一次拍板：谁、为什么、依据哪条授权 | id, actor, role, decision, why, basis, at **+ commitment_version（依据哪一版承诺/报价/SOW）· prior_cases[]（同类事上次谁办、结果如何）· worst_case（不拍板的最坏代价）** | 人（含 Agent 代人） | 永久 |
| **B 卡点**（Blocker） | 一次阻塞：卡在哪、等谁、等了多久 | id, case, stage, waiting_on, since, resolved_by | 任何人/Agent | 永久 |
| **R 突破**（Breakthrough） | 一次解法：什么办法、代价、可复用吗 | id, **blocker_id（必填）**, method, cost, reusable, scope | 当事人 | 永久 |
| **E 经验**（Experience） | 从 D/B/R 里提炼的**可复用条目** | id, from[], claim, evidence[], scope, grade | 只能由人确认 | 永久 |

**关键设计**：E 不能自动生成后就生效。它必须经过一次**人工确认**（谁确认、确认了什么证据），
否则飞轮会变成"AI 自说自话的规则库"——那是最危险的一种沉淀。

## 二之二、还缺四类对象（专家指出，按缺失代价排序）

| 对象 | 为什么不能没有 | 现状 |
|---|---|---|
| **A 授权本体** | 授权要有"谁签的、到哪天、转授链" | **已落**：`Grant` 的 issued_at/expires_at/issued_by/parent 齐备，`Exercise` 判有效期（专家核过） |
| **X 例外（break-glass）** | 现实中每起重大事故都发生在例外里；没有例外就只能绕过，事后无据 | **已落**：`kind: exception`，三条硬约束（必须有理由、签发人、到期且 ≤7 天），加载与写入两口都校验，判定仍走同一个 `Exercise` |
| **N 更正 / 撤回** | 更正只追加，不改写原文 | **已落**：`timeline.Entry.corrects` + `ScanGovernance`（后到者赢，同刻按 id 字典序可重放） |
| **T 废止 / 移交** | 经验/规则/技能要能下线，且要有理由与时间点 | **已落**：`timeline.Entry.retires` + `ScanGovernance`（派生值不落盘，同 Band/Src 纪律） |

**这四类共用同一个判定器与同一条追加式流水** —— 新增对象没有新增第二条判定路径，
那正是"两套答案"的来源。

## 三、飞轮：六步，每步都有出口

```
① 捕获          ② 归一            ③ 评级            ④ 蒸馏
事件发生 → 结构化字段 → 值不值得留 → 提炼成经验候选
   ↑                                                    ↓
⑥ 回流          ⑤ 部署            ⑤' 否决
用得怎么样 ← 进 skill / 进 agent 手册 / 进规则 ← 人确认不过 → 进垃圾池（可复活）
```

| 步 | 做什么 | 判据（可检验） |
|---|---|---|
| ① 捕获 | 每次决策/卡点/突破写进 timeline，字段齐全 | 缺字段的事件**不允许**入库（与服务端同一张规则表） |
| ② 归一 | 同一类事件同一种形状；`derived_from` 串起来 | 任取一条经验，能一路回指到原始事件 |
| ③ 评级 | **影响面 × 不可逆性**，频次只做次要项；另设「低频高损」专道 | 见下面 3.1，公式写进 `metrics.md` 但**权重不由各团队自定** |
| ④ 蒸馏 | 生成"经验候选"（不是经验） | 每条候选必须带：证据链、适用边界、反例 |
| ⑤ 部署 | 进 skill / 手册 / 规则，**带版本与生效时间** | 部署记录可查"谁批的、从哪版起生效" |
| ⑥ 回流 | 用它之后，同类卡点是否减少 | 按月对比：该类卡点出现次数 |

### 3.1 评级为什么是全流程最容易死的地方（执行者的原话）

> 「公式写着客户可改，第一个被改的是权重：各项目组改成自己那版，
> 频次必然压倒影响面。升上来的全是每周导表这类高频小事；
> 真正值钱的一次赔付、一次客户翻脸只发生 1 次，永远评不上去。
> 三个月后大家发现上榜的都是废话，就不往里写了。」

所以评级规则改成三条硬约束：

1. **影响面优先，频次降权**：`score = 影响面 × 不可逆性 × (1 + log2(1+频次))`。
   频次只是对数级加成，**不可能靠"做得多"挤掉"做得重"**。
2. **「低频高损」专道**：影响面 ≥ 阈值（默认：涉钱、涉对外承诺、涉他人数据）的事件，
   **不进普通排序**，直接进蒸馏候选池，哪怕只发生过一次。
3. **权重不许按团队改**：客户可以改阈值与影响面的定义，但**排序原则（影响 > 频次）不可配**。
   可配的只有"多严重算严重"，不能配"什么更重要"——后者一配就被人性吃掉。

**出口**：飞轮必须有"倒垃圾"的口。没有否决与淘汰，三个月后规则库会变成没人敢删的沼泽。

## 四、判据：15 条，逐条可验（并如实标出**现在只有 1 条成立**）

> 第一版这份表写"12 条，第三方可认定"。请治理专家逐条核过代码后，结论是：
> **1 条成立、10 条不成立、4 条无法判定**，且 15 条里有 10 条"标准"写的是我们自己。
> 这一节按他的要求重写成四元组：**对象·字段 | 样本框（范围+抽样） | 一条命令 | 期望输出**。
> 缺任一项不许进验收表 —— 那正是"自说自话"的来源。

### 4.1 认可的标准（只认外部可指的）

| 标准 | 我们真正落实了什么 | 没落实什么 |
|---|---|---|
| W3C PROV | 只在文档里写了"导出时按 PROV 映射" | **没有 `derived_from` 字段、没有导出器、没有 Entity/Activity/Agent 映射**（全仓 0 命中） |
| NIST AI RMF | 审计记录（部分） | 人类监督的证据（判据里一条都没有） |
| IETF AI 治理草案 | 借了"按角色归因"这一句 | **hash 链、签名、外部锚定全没做**；而且该草案明写它管 register 不管逐次流水，我们套错了一层 |
| DMBOK 2.0 | 借了 Owner/Steward/Custodian 三个词 | 五类对象表里**没有 Owner 列**，没人在治理它们 |

**修正**：凡"标准"一栏写"本文第 X 节""执行者第 N 条"的，一律降级为**内部约定**，
不计入"第三方可认定"。真正能挂外部标准的只剩 4 条，其余必须是**可执行命令**才算数。

### 4.2 逐条现状（诚实版）

| # | 判据 | 现状 | 缺什么（可执行地） |
|---|---|---|---|
| 1 | 经验能回指原始事件 | **部分成立** | `derived_from` 已落（timeline + audit），审批与结账两条主链已带；E 仍无持久实体，逐条走链的验法待 P3 |
| 2 | 权限判定只有一个入口 | **不成立** | 至少 5 处：`org.Exercise`、`board.gate.authorize`（注释自称"唯一"）、`org.Viewer.CanSeeDomain`、retrieval 里又实现一遍、policy 派生列 |

| 4 | 账本按角色归因 | **成立**（P1 已落） | `audit.Record.Role` 必填，留空拒收（`ErrNoRole`）；11 处构造点全部补齐；`dev/verify-governance.sh` 实测 60 条记录 0 空值 |

| 8 | 部署可回滚 | **部分成立** | 已有 version + digest + `ledger.jsonl`；缺"哪条经验改了哪个行为"的绑定与基线用例（回滚演练待做） |
| 9 | 破坏性契约变更会被拦 | **不成立** | `gen-types.mjs` 只拦"前端编字段"；删字段、改名同改、标可选三种全绿 |
| 10 | 人能看懂自己的任务 | **无法判定** | 任务卡是手写样例，无版本机制、无生成来源；"撤回"在写路由里不存在 |
| 11 | 人机边界明确 | **无法判定** | 判定树谓词无阈值（多少钱算花钱）；没有答案键、没有"说不清"档 |

| 14 | 同类事可回查 | **部分成立** | `anc blocker recurring` 按 (域, 类别) 归组回答"踩了几次"；卡死不用标题相似度（要调参，调不准就是"看着像"）。缺：客户对象、跨 case 的调派台账 |
| 15 | 待批按最坏代价排序 | **不成立** | `PendingView` 无代价字段、无排序参数；`worst_case` 全仓 0 命中 |

### 4.3 结论与最省力的一刀

- **10 条不成立**里，9 条的原因同一：**字段或接口不存在**（不是"没做好"，是"没有"）。
- 专家给的最省力一刀：**给 `audit.Record` 加必填 `Role`** —— 它同时救活判据 4、
  让判据 3 有意义，而且是全篇唯一"引了外部标准又明确违反它"的地方。

### 4.4 验收形态（以后每条判据都必须长这样）

```
判据 4 · 对象 audit.Record · 字段 Role（必填）
样本框  最近 200 条，按 id 字典序取前 20
命令    anc audit log --json | jq '[.[]|select(.role=="")]|length'
期望    0（退出码 0）
现状    不成立 —— 字段不存在
```

## 五、给非技术同事的一页：人机分工卡

> 目标：**文科职员看完能复述**，不需要懂任何技术词。

### 5.1 一张卡长什么样（五行，一行都不能少）

> 第一版这里是四行，被体验者当面指出：**最先丢掉的是「我不能做什么」**。
> 那一行恰恰是边界。所以改成五行，且每一行都必须自己能站住 ——
> 不依赖读者懂任何系统术语。

```
【这件事】Q3 结算对账          卡片版本 3 · 2026-11-20 起用 · 维护人：李默

① 你要做的
   在「ANC 看板 → 待批」里找到标题为「Q3 结算对账」的那一条，
   读附件三（在「记录」页点这条 → 附件），确认三个数：总额、已收、差额。
   然后点「同意」或「驳回」，各写一句为什么（驳回必须写）。

② Agent 替你做
   收集对账单、核对差异、生成差异表、把三条结论写成一句话交回给你。

③ 你不能做的
   不能让 Agent 替你点「同意」；已经签过的决定不能改 —— 要改就重新提一次。
   拿不准的时候不许硬签：点「挂起」，写清在等谁。

④ 卡住了找谁
   数字对不上（口径问题）→ 找 Bob（财务，飞书搜「Bob」）
   页面打不开 / 报错 → 找 IT（把「记录」里那一行截图发给他）

⑤ 做错了怎么办
   点「撤回」。它会留一条痕，但不会抹掉历史 —— 谁都能看出来撤过。
```

**给读者的自检**：看完这张卡，你应该能回答三句 ——
*我要做什么、Agent 做什么、我去哪儿点。* 答不出，说明卡写坏了，改卡。

### 5.2 判定树（谁来做，5 个人答同一套）

```
① 这件事会不会把别人的东西带到别人眼前？
   （别人的客户数据、别人的报价、别人没公开的结论）
   会 → 人拍板。**注意：删掉文档 ≠ 撤回 —— 对方看到过就是收不回。**

② 会不会花公司的钱 / 改对外的承诺 / 动别人的权限？
   会 → 人拍板（Agent 只能准备材料）

③ 做错了能不能真正撤回（不是"删掉"，是"当作没发生"）？
   能 → Agent 可以做，人抽查
   不能 → 人拍板
```

**第①问是后加的**。原树只判"动作能不能撤"，没判"后果收不收得回"。
执行者给的例子：把 A 客户的续约打法（含真实数据）摘进给 B 的方案 ——
不花钱、不改承诺、不动权限、删文档也能删，按原树 Agent 可做；
但 A 的数据已经进了 B 的视野，截图撤不回来。

**验证方法**：拿 5 个"这件事"的例子，让 5 个不同岗位的人各判一次，
**答案必须一致**；不一致说明规则本身没说清，回去改规则，不是改人。

### 5.3 术语表（给非技术读者的对照）

第一版文档被体验者指出"卡在词上，不是卡在道理上"。凡是非技术同事要读的段落，
行文只用右列的说法；左列的词只出现在工程文档里。

| 我们内部的词 | 说人话 |
|---|---|
| 账本 / timeline / audit | **记录**（谁在什么时候做了什么） |
| 视图（按人检索是视图） | **查法**（按人查只是个筛子，记录本身不按人存） |
| 血缘 / derived_from | **出处**（这条结论是从哪几件事推出来的） |
| 契约 / 契约漂移 | **接口格式** / **格式对不上了** |
| 装配 / pack | **准备材料**（给某个 Agent 的那一份） |
| 归一 | **统一格式** |
| 蒸馏 | **提炼**（把几件事归纳成一条经验） |
| 部署经验 | **发下去用**（进手册、进规则） |
| 回流 / 度量 | **看看有没有用** |
| 门禁 | **过关条件** |

### 5.4 写给人看的三条纪律

1. **每一句都要能独立站住**：不出现"见上文""如前所述"。
2. **名词后面的第一句必须是动作**：不是"口径需确认"，而是"去确认这三个数"。
3. **凡是指路，必须给到可点的位置与人**：页面名 + 条目名 + 找谁怎么找。

## 六、专家会怎么测（我们的测试协议）

### 6.1 三种测试，缺一不可

| 测试 | 谁来做 | 判据 |
|---|---|---|
| **可理解性**（普通人） | 非技术同事 | 看完一页能复述"我做什么、Agent 做什么、卡住找谁" |
| **一致性**（专家） | 数据治理/审计视角 | 用第四节 12 条逐条打分，能指出哪条不成立并给反例 |
| **可用性**（当事人） | 真实岗位 | 完成一次"签"不超过 3 步；出错时能自己恢复 |

### 6.2 用 Agent 模拟评审（本轮就做）

下发三个人设，各自独立看同一份材料，不许互相参考：

1. **体验者**（行政/文科，非技术）：只问"我看不看得懂、我下一步做什么"
2. **执行者**（一线负责人）：只问"我要拍板时，界面/手册够不够我下决定"
3. **策划者**（数据治理专家）：只问"这套东西能不能被第三方验、哪里是自说自话"

三个人的结论**取交集**才是可信的；只有一个人说好，说明只对那一种人好。
