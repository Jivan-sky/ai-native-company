# 身份、组织与能力（方向备忘）

> 2026-11-12 口述整理。这不是实现计划，是**边界**：哪一层归飞书，哪一层归 ANC，
> 哪一层谁都不该碰。写下来的理由是：这三层一旦混在一起，后面每接一个系统都会再混一次。

## 三层，不要混

| 层 | 回答 | 归谁 | 同步方式 |
|---|---|---|---|
| **认证** | 你是谁 | 飞书 SSO | 一次性，登录即得 |
| **组织** | 你在哪个部门、向谁汇报 | 飞书通讯录 | 定期同步，**我们不编辑** |
| **能力** | 你能对什么做什么 | **ANC 自己** | 人维护 + 规则推导 |

飞书给的是一张**组织图**，不是一张**权限图**。销售总监在飞书里是「销售部负责人」，
在 CRM 里要的却是「看全部销售的业绩」——这条不在飞书里，也不该在飞书里。

所以：**SSO 解决「是谁」，解决不了「能做什么」。** 后者必须是我们的一张表。

## 能力表长什么样

不是「角色 → 页面」，是「角色 → 能力」：

```
能力 = 业务模块 × 动作 × 范围

业务模块   CRM | ERP | 工单 | 工程管理 | 数据 | 作业 | 审计 | 成员
动作       read | write | approve | execute | admin
范围       all | 本部门 | 本人 | 指定对象
```

例：`销售总监 → crm.read(范围=all)`、`销售 → crm.read(范围=本人)`、
`工程负责人 → jira.read(范围=本部门)`。这张表住在 `internal/org`，跟 grants 同一处。

## 密钥：两件事，别合成一件

「密钥完全依靠 SSO」——**一半对，一半要拆开**：

1. **ANC 自己的登录凭据**：完全交给 SSO。我们不存密码、不做本地账号。
2. **接进 ANC 的那些系统的凭据**（CRM / ERP / 工单各自的 API key）：
   那些系统不认飞书令牌，它们只认自己的 key。所以 ANC 必须**托管**它们。

托管不等于人人可用。正确的形状是：

```
key 存在服务端（不进前端、不进 spec、不进看板）
  ↑ 谁能用哪把 key，由能力表决定
  ↑ 用的时候由 ANC 代理调用，人拿不到明文
```

也就是说：**SSO 决定「谁在用」，能力表决定「他能用哪把 key」，key 的明文永远不出服务端。**
这跟现有的 `internal/authz`（令牌、预算、撤销、留痕）是同一条纪律。

## 这决定了产品形态

「更低的价格 + 更先进的智能化」不是一句定位，它有一个硬性架构后果：

> **不能一家一家定制集成。** 定制集成是最贵的那条路，价格永远压不下来。

所以接入必须走**统一的连接器**：一种 spec 描述「连什么、怎么认证、拉什么、落到哪」，
新增一个系统是写一份 spec，不是写一个项目。仓库里「接入」页已经是这个形状的第一版
（`anc.job/v1`）——它现在能接 HTTP 与已审批的应用，下一步是把 CRM / ERP / 工单这类
**有状态系统**接进来。

## 目标客户决定了取舍

客户画像：高速增长期公司，没走完 C/D 轮，**没有真正的 ERP / CRM / 工单系统**。

- 他们不缺「更强大的 ERP」，缺的是「一套能一起用的东西」；
- 所以我们不跟传统厂商比稳定、比功能覆盖，比的是**接得快、看得懂、改得动**；
- 「让企业适应我们的同时，我们去适应企业」——落到工程上就是：能力表可改、连接器可加、
  页面可裁，而不是每家一套代码分支。

## 已经做掉的第一步（2026-11-12，不依赖飞书）

| 件 | 落点 | 现状 |
|---|---|---|
| 能力表 | `<vault>/capabilities.md`（角色 × 模块 × 动作 × 范围） | ✅ 读不到 = 空表 = 全拒，不是错误 |
| 身份口子 | `--identity-header`（默认 `X-ANC-User`）→ `org.Member` 查岗位 | ✅ 飞书接上后由 SSO 回填同一个头，判据不动 |
| 路由判定 | `internal/board/identity.go` 的 `capabilityGate` | ✅ 按**路径**判，不按 Kind（KindRead 里既有首页投影也有审计） |

实测（`--enforce-authz` 打开，真跑）：

```
无身份                 → 401
X-ANC-User: alice      → 200   （manager 有 audit.read）
X-ANC-User: devbot     → 403   {"error":"「devbot」（岗位 devbot）没有 audit.read 的权限", ...}
X-ANC-User: devbot     → 200   /api/board（board.read 有）
X-ANC-User: nobody     → 403   （名册里没有这个人）
```

**默认不开**（`EnforceAuthz=false`）：开发机上没有网关、没人往 header 里放身份，开了等于把看板锁死。
生产环境打开它，隔离才是真的。

## 还没做（依赖飞书或下一步）

1. **飞书 SSO 换身份**：等 App ID / Secret / 回调。换成之后只改 `resolveIdentity` 一处。
2. **条目级范围**：`scope` 列（all/dept/self）现在只用于判定，不用于过滤行 —— 要真身份 +
   部门树才能做「张三只看本部门」。
3. **拒绝也要留痕**：现在 401/403 只回给调用方，没进 audit。审计是客户的账本，得先想清楚
   记什么、记多少（看板自己的埋点已经明确不进 audit，见 DECISIONS #7）。

## 第一步（不依赖飞书就能做）

1. **身份入口留一个口子**：`board serve` 接受来自网关的 `X-ANC-User`（内网可信 header），
   现在先手工传，飞书接上后由 SSO 回填 —— 判据不动，只换来身份来源。
2. **把 capability 表写出来**（业务模块 × 动作 × 范围），先只用于**判定**，不改页面。
3. **路由能力表接进中间件**：`inventory.go` 的 Kind 已经在了，只是没被用来判定；
   `/api/audit` 这类不该再匿名可读。

这三件做完，「谁能调用哪段逻辑」才是真的；页面级的显隐只是它的投影。
