# 上下文治理：现状与缺口

> 2026-11-14。这个模块是项目最早的东西，但一直是**只读展示**，不是治理。

## 一、现在有什么（在读真服务上量的）

`GET /api/context?who=alice` → `anc.context/v1`，结构：

```
roster[]   谁在这家公司（成员 + 业务 agent），每条带 evidence{file,line}
pack {
  who, at, identity
  domains     我能看的业务域
  directory   我能用的数据目录
  projects    我在办的项目
  grants      我被允许做什么（按主体滤过）
  gaps        缺什么（3 条）
}
```

**做对的地方**：每一条都能回到原文（`evidence` 是 `agents.md:5` 这种）。这是"可追溯"那根柱子的底子，不能丢。

**做错的地方**：它是一个**快照**，不是一个**治理面**。具体四缺：

| 缺 | 后果 |
|---|---|
| 缺"为什么有 / 为什么没有" | 读者看到 3 条 gaps，但不知道是哪条规则挡的；想改也无从下手 |
| 缺策略编辑 | 谁能看哪块、哪一列要脱敏、哪些字段不许出 —— 全在 `domains.md` / `company.md` 里手写，界面只能看 |
| 缺预算 | 上下文有 token 上限这回事，但界面没有"这次装配占了多少、超了会砍哪一段" |
| 缺"装配前后对照" | 给出的上下文和原始资料之间没有 diff：被裁掉什么、被脱敏成什么，看不见 |

## 二、治理该长什么样

一句话：**它要能回答"这个 agent 为什么只拿到这些"，并且能当场改。**

```
上下文（谁）
├ 装了什么      按段列出：身份 / 域 / 目录 / 项目 / 授权 / 待办，每段带 evidence
├ 为什么是这些  每段一句"按哪条规则进来的"；没进来的写"被哪条挡在外面"
├ 预算是多少    这一段占多少 token，上限多少，超了砍谁（按优先级）
└ 改规则        直接跳到那一行原文去改（不能编辑时，给"打开那一行"）
```

关键是第三、四项：**没有预算的上下文治理是假的**——装配器想给多少给多少，
最后一定演变成"把整个 vault 塞进去"，token 账单爆掉，而界面看不出来。

## 三、最小的一刀（建议下一步做这个）

不动装配逻辑，只把**已有的信息摊开**：

1. `/api/context` 每段加 `why`（依据哪条规则 / 为什么被排除）与 `chars`（这一段的字符数）
2. 页面上每段一行：`段名 · N 字 · 依据 xxx · 打开原文`
3. 顶部一行总账：`本次装配 N 字（上限 M）`，超了就红

这三件事全部基于已有数据，不需要新造机制；
但做完之后，"上下文"从"看看它给了什么"变成"能不能给出一个说得清的理由"。

## 四、我为什么现在只写这个不写代码

这一轮的话我说实话：这个模块要动的是**装配器与策略层**（`ctxpack` + `org` 的规则表），
不是界面。改它需要能跑通"改规则 → 重新装配 → 对比前后"的完整回路，
半截改法只会让"看起来治理了、其实还是只读"更糟。

所以我把缺口写清楚，把最小的一刀定成"摊开已有的依据"，下一轮从这里开始。
