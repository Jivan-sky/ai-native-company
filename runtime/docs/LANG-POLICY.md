# 多语言策略：哪里可以混、哪里不能

2026-11-15。你问「能不能把 TS 或 Python 拉进来」。答案分三种混法，代价差别很大。

## 一、先认事实：我们已经在混

**TypeScript 早就在里面了** —— `boardui/src/*.ts` 经 esbuild 打成 `app.js`，再 `go:embed` 进二进制。
它混得毫无代价，因为它是**构建期**语言：产物是静态文件，运行时只有 Go。

所以真正的问题不是"要不要混"，是**在哪一层混**。

## 二、三种混法，代价完全不同

| 混法 | 例子 | 运行时要什么 | 代价 | 我们的判断 |
|---|---|---|---|---|
| **构建期**（产物进二进制） | TS → app.js | 无 | ≈0 | ✅ 已经在用，可以继续扩 |
| **伴生进程**（同一台机、独立进程、走本机 HTTP/socket） | Python 适配层 | 多一个运行时 | 部署多一步、故障面多一处 | ⚠️ 作为**可选插件**可以 |
| **双核心**（业务规则两边各写一份） | Python 里再实现权限/审计 | — | 迟早不一致 | ❌ 不做 |

第三条是红线。我们花了整轮把「权限判定 / 审计双流水 / 写盘事务」做成一处真相；
在 Python 里再写一份，等于把已经修好的不变量重新弄坏。

## 三、各层该用什么语言（明确边界）

| 层 | 语言 | 理由 |
|---|---|---|
| 真相源与业务规则（org / grants / audit / tasksettle / intake） | **Go，唯一** | 一处真相，别处不许再实现 |
| 看板前端 | **TS（构建期）** | 已经在用；零运行时代价 |
| 契约校验 / 类型生成（开发期脚本） | **TS 或 Go 都行** | 不发货、不进二进制，随便选顺手的 |
| Agent 面向动作的接口（`/agent/*`、MCP） | **Go** | 要复用权限与审计 |
| Python 适配层（可选） | **只做协议转换** | 让 Python 生态的 agent 能用；业务仍回 Go |

## 四、Python 能进来，但要遵守四条

如果确实要一个 Python 壳（比如客户用 LangChain / CrewAI，只有 Python SDK），它可以存在，但：

1. **它不碰凭据**：机器令牌从 Go 发，Python 只转发，不落盘。
2. **它不实现业务规则**：权限、审计、幂等一律回到 Go 的接口；Python 只做翻译（HTTP ↔ SDK 对象）。
3. **它不参与默认安装**：基础交付仍是单二进制；Python 壳是 `extras/` 里的可选件，装不装不影响主程序。
4. **它必须能被删掉**：删掉之后产品功能一条不少 —— 这是"可选件"的定义。

## 五、TS 还能多干一件事（零运行时成本）

现在 TS 只做 UI。可以让它再承担**契约校验**：

- `dev/gen-types.mjs`：读真实 payload（`/tmp/contract/*.json`），与 `core/types.ts` 逐字段比对，
  不一致就退出非零。
- 这一步等于那份 contract-first prompt 里的 OpenAPI 校验，**不引入任何运行时**。

这是"把 TS 拉进来"最划算的方式：不增加部署面，却把"契约漂移"变成会自动失败的检查。

## 六、一句话

**混语言不是目的，把每种语言的强项放在正确的那一层才是。**
构建期随便混（产物进二进制，零代价）；运行期要混，只能是"可选、可删、不碰真相"的伴生件。

## 七、待你拍

2. 我建议先做 `dev/gen-types.mjs`（TS 构建期校验）—— 它不增加任何运行时，却能挡住我们最怕的契约漂移。
