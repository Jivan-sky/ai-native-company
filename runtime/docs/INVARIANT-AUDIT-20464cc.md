## A1　任务结账

**高严重度。** Redis 保存进行中的唯一状态，结账应在对应任务实例的终态持久化后清理热层。当前 `settledEntry` 遍历时间线，普通记录只要与任务同 case 就算“已归档”。调用者在检查任务是否仍在进行之前就删除热层并返回 `Already`。另一条路径先读任务，再写终态，最后按 ID 无条件删除，中间成功的交接可能被抹掉。[权威边界](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L304-L320) · [结账顺序](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/tasksettle/tasksettle.go#L70-L108) · [归档行及匹配谓词](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/tasksettle/tasksettle.go#L119-L158) · [删除操作](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/hot/redis.go#L606-L615)

### 合法转移

| 起点 | 动作 | 结果 |
|---|---|---|
| `queued / running / review / blocked` | 普通结账 | 返回仍在办理，保留版本、持有人、有效租约和现场。 |
| 进行中 | 对眼前版本显式取消或判失败 | 记录操作者、决定时间和实际终态。显式传入 `running` 等非终态仍不能结账。 |
| `done / cancelled` | 普通结账 | 将该实例的终态归档。业务 `failed` 映射到协议阶段 `done`，归档和统计须保留失败结果。 |
| 已有该实例的正式结账回执 | 重送原请求或补清理 | 回原决定，只补缺项。提出相反终态时返回冲突。 |
| 老数据缺 `stage` | 尝试归档 | 按现有映射从已知 `status` 还原；无法从自定义词判定终态时保留现场、返回原因。 |

`ack` 或 `verify` 负责改变业务状态，`settle` 负责显式归档。普通任务可按现有规则回执完成；进入验收的任务仍支持驳回重提。[阶段及版本契约](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/README.md#L569-L590) · [旧状态映射](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/hot/hot.go#L275-L312) · [结账设计原意](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/DESIGN.md#L3565-L3582)

### 版本、唯一键与写入顺序

- **一个实例只结一次。** 业务唯一键为 `(vault, task_instance_id, settle)`。可复用的业务编号须配不可复用的实例号。同一 case 可含多个工作项。作者、月份、业务结果和版本均不能使同一实例获得第二个结账位置。
- **版本决定请求是否仍合法。** 结账带操作者看到的 `expected_version`。取得与其他任务写者共享的串行保护后，重新读取该实例的版本和阶段，再决定能否提交。新旧客户端都要保护本次读写窗口；旧客户端未传版本时，只能保证服务端本次读到的版本。租约围栏仍用于持有人操作。
- **请求号决定是否重放。** 同一 `request_id`、目标版本与业务参数返回原回执；请求号复用但参数冲突时拒绝。服务端处理重试应先核对已有回执，避免把已成功的同一请求误报为版本陈旧。
- **提交点是 vault 中不可覆盖的结账回执。** 它包含实例号、原版本、终态、操作者、原决定时间、稳定的时间线事件 ID、验收口径、评审人及提交时的证据引用。结账补充的引用与原引用合并。原任务的 `refs` 目前只在热层积累，归档入口单独取本次参数。[验收材料的写入](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/hot/task.go#L374-L391) · [当前归档字段](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/tasksettle/tasksettle.go#L115-L142)

写入顺序为：串行核对实例与版本 → 持久创建唯一回执 → 按稳定事件 ID 写终态时间线 → 条件清除对应实例、版本或结账占位的状态、租约和围栏。回执已提交后，该实例在业务上已经结束。所有能改同一对象的入口，包括交接、回执、人工热层操作和新建同名任务，都要能看见该决定。只在最后删 Redis 时比版本，会留下与已成功交接冲突的旧版终态。[交接的 CAS](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/hot/task.go#L323-L345) · [结账的存储接口](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/tasksettle/tasksettle.go#L23-L43) · [看板、CLI 与 MCP 的共用入口](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/board/tasks.go#L16-L34)

## A2　审批裁决

**高严重度。** 看板、CLI 和卡片走同一裁决入口。当前顺序为读待批 → 追加时间线 → 追加审计 → 删除待批。两位操作者都可能先读到待批、各自成功写下相反决定。即使只有一位操作者，第二笔写失败后重试也会重复追加第一笔。当前顺序重复点击测试发生在第一次已成功清队之后。[规范](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L718-L731) · [两笔留痕与幂等预期](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/DESIGN.md#L1935-L1962) · [裁决顺序](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/approvals/approvals.go#L419-L445) · [现有重试测试](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/approvals/approvals_test.go#L262-L302)

### 合法转移

| 起点 | 动作 | 结果 |
|---|---|---|
| 本轮待批 | `approve / reject / hold` | 第一个合法且成功持久提交的裁决结束本轮，固定信号、操作者、理由和原时间。 |
| 已裁决、流水或清队待同步 | 重送原请求 | 返回原裁决号和同步进度；后台继续补缺。 |
| 本轮已裁决 | 另一请求提出相反意见 | 返回冲突和调用者有权看到的既有裁决；不新增第二个终局。 |

### 两项修复的持久性边界

适用前提是一家公司使用一份权威持久卷，各进程共享同一串行裁决机制。权威回执必须完整且不可覆盖，投影操作可重复执行。JSONL 的每个写者应在同一分片保护下按稳定事件 ID 查重，ID 和原始内容一致才认领已有行。恢复进程在“行已写入、进度尚未标记”的窗口只补记进度。发现半行、同 ID 异内容、历史相反裁决时，保留证据并报告待核对。回执的原子创建、数据同步和目录元数据持久化须按交付平台验证。进程退出与机器断电分开验收。[现有 JSONL 追加](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/timeline/timeline.go#L210-L248)

启动时扫描未完成回执并补账；请求重试也可触发同一恢复逻辑。验收同时清点持久回执、两个分片中的逻辑事件、Redis 的实例和版本，以及用户所见回执。已持久裁决但尚未投影时，读端应显示同步中，不能再提供一个可成功的裁决入口。对旧数据，仅凭证据一致性足以唯一归因时自动补齐；缺少可信依据时不给历史决定补造身份或胜者。

## A3　跨域授权何时失效

**高严重度。** 一笔委派登记在册，只证明它曾经签发。SPEC 要求每次行使检查授权者的有效权限与在职状态，子委派不能活得比上游授权久。当前 `Grant` 保存相对期限文本，信封准入对跨域行使检查受予者和域，尚未判动作、到期时刻及授权来源链。下文针对跨域**业务动作的准入**；收件、动作执行成功和审批通过分别留各自的事实。[授权字段](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L575-L588) · [角色、级联与期限](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L641-L664) · [现有记录结构](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/org/grants.go#L22-L33) · [准入边界](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/envelope/gate.go#L15-L36) · [当前匹配](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/envelope/gate.go#L167-L179)

### 有效授权的判据

以“采购岗的乙能否读取贸易域”为例，参与判定的是 **谁实际调用、代谁行使、读什么对象、在什么时刻、依据哪版授权事实**。同一动作应得到可解释的结果。以下是建议写回 SPEC 的契约。

1. **保留签发时的来源。** 每笔授权有稳定 ID，记录授予者、受予主体、动作、带类型的客体、签发生效时刻、可选到期时刻，以及此次签发所依据的上游授权 ID 或客户确认的根授权。岗位派生的授权还要能定位这一次任职。旧工号或岗位名复用时，不能把旧任职的授权接给新任职。根授权如何创设属于本报告 C1；验收以一笔已明确的根授权为起点。
2. **逐段验证，再合并独立依据。** 一条链有效，要求每一段在判定时刻都已生效、未到期、未撤回，授予者当时仍持有该项权，当前受予者仍满足在职、任职或代理条件。子项的动作、客体与范围不得超出父项；无法证明可包含时，只接受明确匹配的范围。中间一段失效使该链的全部后代失效。一人持有两条独立链时，另一条完整有效链可以支持本次行使；失效的子授权不能自行改挂到备用链。保留历史行以供回溯。
3. **区分离职、换岗与撤回。** 离职生效后，当事人本人的工作授权及以其授权为来源的后代均失效，代其行使的 Bot 同样失去这项权。换岗只终止依赖旧任职的链；来源明确、与岗位无关且其他条件仍满足的个人直授权继续有效。按 SPEC 的“岗位生成默认授权集”，建议把岗位模板签发为**绑定任职实例的具体授权**。新任职须能找到对应的新授权，调回原岗也不复活旧授权。业务 Bot 代岗位时核对其已登记的岗位代理关系，与员工本人的任职授权分别计算。
4. **统一时间边界。** 按权威服务时钟比较，采用左闭右开区间 `[生效时刻, 到期时刻)`；恰在到期时已经失效。空期限沿用 SPEC 的无固定截止，但仍受上游期限、离职及撤回约束。相对期限从有证据的签发生效时刻换算一次；重读或重新部署不能刷新起算点。续期产生一笔新的授权，已到期记录仍可查询。
5. **选定生效点。** 建议以有序的权威授权版本生效为准。一次判定使用同版的组织任职、代理关系、授权和撤回记录；换岗的旧任职结束与新任职变更按同一已提交版本读取。在权威版本确认撤回后开始的行使，应看到新版本；本地副本不能确认已追平时，结果为“无法判定”，不放行。预演结果只描述其评估时刻和版本。若收件会排队，真正开始受保护动作前再判；跨越边界的已执行动作保留当时的依据。现有 Git 周期同步不足以证明上游即时撤回，生效点选择与 C2 联动。[副本同步](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L343-L350) · [撤回承诺](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L656-L664)

**签发、撤回与重试。** 签发时核对授予者在该版本已拥有可授出的同一权限，把授权与其上游依据一并持久记录，保留产生它的审批或根授权引用。撤回以授权 ID 为目标追加撤回事实，重复投递同一事件不产生第二次生效；历史回放仍可得到撤回前的结论。当前判定沿原链读取最新有效状态，无需等后台逐级更新所有子项。缓存须同时受快照版本和链上最早到期时刻约束。

**存量与失败处理。** 有可信签发记录的旧授权可补齐起算时间与来源；仅凭文件修改时间、当前同名岗位或目录顺序不能补证。旧 `to: role` 记录需要区分模板与已授给某次任职的有效权，先列受影响的授权与成员，再按可证明的任职映射转换。链中出现循环、缺父记录、期限无法解释或权威数据读失败，且无其他可证明的有效链时，两端均返回“无法判定”并给出待修的数据项。已知到期、已撤回、已离职返回“拒绝”及具体原因。建议先对照输出新旧差异，再按同一策略版本切换基准、预检和正式入口。

### A3 验收：每条反例都查两端

以下主体均已认证；除特别说明，乙不属于贸易域，目标统一为 `read / domain:trade`。给两端提供同一权威快照与受控时钟。对“拒绝”和“无法判定”，正式入口均不得启动受保护动作；基准的权限需求均不记为已送达。

| A3-7 旧资料不全 | 唯一候选旧授权只写期限 `30d`、无可信起算点；另分别考察缺失父项和父链循环 | 三种情况均能终止判定并指出缺口，基准不记绿，准入不放行。补齐可信依据后再判；未补齐前不能静默解释为永久或根授权。 |

### A4 验收：逐项对账，包含正向对照

对每行使用同一批权限数据，依次从基准、信封预检和正式入口读取**授权结论**。除特别说明，时刻与版本固定。清点每项的结果、原因、证据链和实际行使次数；预演与基准不得增加实际行使计数。

| 编号 | 最小事件顺序 | 验收预期 |
|---|---|---|
| A4-1 正确受予者与仅署名者 | G 由甲授予乙；S 只在该授权行署名，S 自身无此权 → 乙、S 分别请求同一动作和域 | 乙三端均允许、证据为 G；S 的相关列表可展示 G，但三端对 S 均拒绝，其 grant 项未送达。甲如有权，应从其自己的上游依据得到允许，不能拿发给乙的 G 证明自己持权。 |
| A4-2 动作和方向 | 乙只有贸易域读权 → 分别读贸易域、写贸易域、读另一域 → 再查反向受予关系 | 仅第一项允许。其余分别报告动作、客体或有效受予主体不匹配；三端逐项一致。不能从某域一项能力推出任意动作或反向授权。 |
| A4-3 岗位与代理 | 旧记录只写岗位模板，无具体任职授权 → 为现任乙生成 G → 由其绑定 Bot 代乙申请行使；再用无有效代理绑定的模拟主体作对照 | 模板阶段三端均不能把乙判为已获权；生成 G 后乙及有效代理均能引用该具体依据。没有有效代理绑定时三端均不通过，不能改按 Bot 自身或另一个同名主体判。乙换岗后按 A3-3 对账。 |
| A4-4 到期和缓存 | 基准在截止前通过 → 到达截止时刻再做预检和正式准入 → 按新时刻重跑基准 | 截止前的历史结论可复查；截止时刻的三端均拒绝，原因及过期授权一致。同一授权数据版本、不同评估时刻也能产生不同结果。 |
| A4-5 旧题、旧信封与别名 | 同一域分别用规范化引用与无歧义裸 slug 表示；再提交只有 `read` 的基准题、无法归域的目录名或不能确定业务动作的跨域信封 | 前两种表示三端结论和证据一致。缺对象或缺动作的输入显示具体缺项，不能以任意一行 read 授权判绿；若统计单列，报告同时显示未覆盖数量。 |
| A4-6 申请和行使 | 无权的在职主体先提交纯申请，再尝试同域同动作的实际行使；另以旧告警策略对照 | 申请可进入审批并标为“请求”，其业务权限仍未就绪；实际行使拒绝。观察模式的告警收件可单报，不能进入“有权行使”的通过数。 |
| A4-7 结论与副作用 | 同一份有效 G 先经基准、预检、正常准入；再令准入后的收件持久化失败 | 正常时三端授权均允许且指向 G；只有实际入口产生行使尝试。后一次授权结论仍为允许，但收件失败可见，不能当作业务执行成功。审计写失败的恢复由 A5 独立处理。 |

验收时应保留两种对照：对确定有效的 G，三端都应引用同一笔或同一条有效链；只改变受予者、动作、时刻或权威版本之一时，三端都应给出表中预定的答案。这样即便三个入口共用了一个仍然写错的函数，错误也能被独立的业务预期识别。

## A5　准入、收件与审计的成功边界

**高严重度 · 双写与回执语义。** 出站读取的审计追加异常只写 stderr，调用者仍可能收到正文；入站信封则先写跨域准入的 `ok`，后写信封，后一步失败时客户端收到“这次不算数”。前者丢了每次读都应有的账，后者让一笔准入记录看起来像已收件。SPEC 把信封日志放在运行态 data，把审计账放在 vault。以下方案保留这两个归属，覆盖应留痕的跨域入站尝试和 MCP 上下文读，不把所有同域流量扩大为审计对象。[存储分工](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L304-L309) · [出站读留痕要求](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L676-L685) · [出站响应](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/envelope_read.go#L49-L62) · [写失败处理](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/envelope_read.go#L84-L111) · [入站顺序](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/envelope.go#L959-L982) · [跟踪议题 #71](https://github.com/Jivan-sky/ai-native-company/issues/71)

**设计取舍。** 对受审计约束的读，建议审计不可用时暂缓返回正文。只读接口不需要为此复制一份敏感响应；日志仅保留目标、版本、结果、原因类别等既有可记录字段。入站已经持久收件时允许如实回部分成功，避免用户因为审计暂不可用而重复发送。完整成功、部分成功和结果未知均应带可查询的关联号。[现有信封脱敏](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/envelope/log.go#L45-L75) · [审计写口](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/audit/audit.go#L236-L282)

### 部分写入的恢复协议

1. **分清业务请求和调用尝试。** 入站以“组织、可信发送主体、客户端稳定请求 ID”识别同一逻辑收件，按规范化业务内容比较指纹，排除重试时新生成的服务端时间。相同键相同内容只认领原收件；相同键异内容返回冲突，拒绝覆盖。实际重投另有尝试 ID；投影恢复沿用原尝试和事件 ID。现有无 ID 请求由服务端按时间补号，跨网络丢响应时无法据此识别同一业务；兼容旧客户端时明示此限制，能重试的调用方应事先保留业务键。[当前补号](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/envelope.go#L911-L923) · [当前审计 ID](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/envelope.go#L1053-L1077)
2. **先有可恢复的事实，再作成功声明。** 对应留痕尝试，先持久记录最小工作项，固定操作、尝试 ID、阶段、原时刻和脱敏审计所需字段。跨域允许后，在 data 按业务键原子认领收件，完整记录直接作为收件凭据；追加式布局也须保证各写进程按同一键串行核对、写入和同步。入站被拒只产生拒绝痕，收件数保持零。若无任何可写的持久落点，只能拒绝提供成功服务并报告“留痕故障”；一次从未持久记录的尝试无法事后还原。
3. **恢复只补已经能证明的阶段。** 启动或周期恢复时按原键查收件与审计。已有完整收件只补缺失的审计，保留原决定时刻与授权版本；仅有准入意向、无完整收件，不登记已收，也不靠恢复程序重做业务。调用方实际再发且此前尚未收件时，作为新尝试按当前权限重判。若已写一行但进度标记没更新，按事件 ID、分片、内容核对后认领；同键异内容或残行保留现场，进入待核对。成功口径须在目标平台验证完整写入及同步，单凭 `O_APPEND` 或写到 stderr 不兑现掉电恢复。
4. **发布状态与历史对账。** 出站失败时只补原尝试的故障痕，不在后台重新释放正文；后续真实读取重新判权并记录自己的尝试。入站回执可重查已知的收件状态，单独标明审计状态。旧的跨域 `ok` 若不能可靠关联到完整信封，只标“准入已有记录，收件未核实”。不能依据同一秒、同主体或相近文本推断为已收件。

## A7　MCP 读取知识时如何核对签发原件

**中严重度 · 来源在建索引时丢失。** 规范要求整理稿的 `source_file` 指回追加保存的签发件；出现分歧时应能打开原件核对。目前索引会剥离 frontmatter，只留下文档路径、业务域、标题、正文和文件修改时间。`anc_get` 返回的 `path` 是整理稿位置。哪怕把唯一的签发件从 A 更正为 B，只要正文相同，MCP 的读者仍无法据此选对原件。这里审查 MCP 出口；直接读取获准的 vault 文件仍可能找回原始字段。[原件与整理稿契约](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L263-L284) · [发生分歧时的核对规则](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L550-L555) · [索引字段](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/retrieval/retrieval.go#L375-L388) · [当前 MCP 正文响应](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/search.go#L345-L366) · [跟踪议题 #73](https://github.com/Jivan-sky/ai-native-company/issues/73)

### 从入库到打开原件

1. **入库保存有版本的引用。** 沿用 Markdown 的 `source_file`。建议将“这版整理稿 → 哪个原件、哪一版”作为可验证的关系：整理稿版本覆盖正文和来源元数据，原件有独立的对象标识及不可变版本或内容摘要。改正误指时写入新的来源关系并保留旧版本。同一正文的散列、文档标题和文件修改时间都不足以标识该关系。历史资料只有路径时，可按已登记规则唯一解析；无法证明历史版本时明确标为未核实，不猜同名文件。
2. **索引携带关系，原件仍按需打开。** 索引构造时解析并保存来源引用；查正文时从同一文档版本组装正文与来源。索引重建后应重现同一关联，不需要将 PDF、图片或整个 `_originals/` 纳入全文索引。可复用客户已授权的原件打开入口；若提供 MCP 解引用能力，它只接受服务端签发的引用，且在返回内容时复查权限。引用不能当访问凭证。[当前按可见索引路径取文](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/retrieval/retrieval.go#L254-L279) · [默认跳过原件目录](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/retrieval/retrieval.go#L343-L357)
3. **保持旧响应可用。** 建议给成功的 `anc_get` 增加 `document_version` 和结构化的 `source`。原有 `path/title/domain/body/total_bytes/truncated` 语义保留。允许核验时，`source` 返回状态、稳定引用、所指版本及受控打开方式；正文被大小上限截断时，这些字段仍单独返回。引用应绑定组织和文档版本；解析旧引用仅可得到旧目标或明确的不可用结果，不能静默指到最新版。

### 响应口径

以下状态名均为提案。一次成功取回正文、一次成功定位原件、一次成功打开原件分别记账。建议只在真正打开并核对指定版本后表示“原件已核验”。

| 条件 | `anc_get` 返回什么 | 请求打开原件时 |
|---|---|---|
| 正文可读，来源及目标版本可定位，调用者可打开 | 正文成功，`source.status=available`，给可使用的引用和版本 | 当场重新判权、核对目标版本，成功才提供该版原件或受控打开结果。 |
| 允许知道原件身份，无权读取内容 | 正文成功，`restricted`，只给获准公开的标识和申请访问方式 | 拒绝；不返回原件字节、存储路径或可直接下载的地址。 |
| 不允许知道目标是否存在 | 正文成功，仅给 `unavailable`。若连来源关系也受限，则对有无来源统一使用此形状 | 对未授权主体，真实存在、缺件和无法访问的目标使用同一公开结果，不给文件名、标识、可枚举细节或真实路径。 |
| 允许核对来源及存在性，可信存储确认该目标或所指版本缺失 | 正文成功，`missing`，说明“有来源登记，指定原件不可得”，提示维护人核实 | 无原件返回。不得用同名件、相近版本或整理稿替代。 |
| 允许诊断，但未登记、引用无效、版本不符或存储暂不可用 | 分别给 `unlinked`、`invalid_ref`、`version_mismatch` 或 `temporarily_unavailable`；正文仍可读 | 未登记请补录，有歧义请修复，暂时故障可重试。只有存储能确认缺件且权限允许披露时返回 `missing`。 |

如果业务动作要求“以签发件核实”，收到正文或收到 `available` 都不能宣称已核实。审计按 A5 记录真实动作及结果，使用受控标识与版本，避免把原件内容或内部存储位置写进普通调用者可见的日志。

### 失效与重新核验

1. **生成后复查。** 来源仍为同一确认结案、引用版本可核对且草稿内容与核验记录一致，才可沿用该次核验。与结案依据无关的备注只增加历史；不应使所有草稿一律返工。
2. **重开立即失去当前发布资格。** 取 B1 权威状态：已重开、出现未决冲突或无法确认唯一头时，候选、草稿检查和发布入口给出相同原因。旧稿仍可解释 D1 当时的决定。证据依赖被纠正、同路径内容不符或人工修改了可执行步骤，也要求相应部分重新核验。已发布版本单列“来源受影响”，供责任人评估撤回或换版，不能静默替换宿主正在使用的文件。
3. **D2 再次结案后逐项对照。** 从 D2 提取新证据清单，与 D1 比较新增、更换、撤回及保持不变的依据。对受影响步骤记录“保留、改写或删除”、判断人、理由和验证结果；未受影响步骤可复用有证据的旧结果。即使正文无需改，仍产生绑定 D2 的新修订和核验记录。不能仅把旧稿的 `case` 或闭环 ID 改成 D2。
4. **发布提交点再次核对。** 以草稿修订、结案事件和证据清单版本作为条件，同步核对 B1 当前头与 A6 实际发布字节。核验后、发布前若有新重开、证据变更或新编辑，返回差异，保留审核材料。对同一核验请求的重试返回原记录。对存量草稿，仅在历史材料能唯一证明其闭环和依据时补建关联；否则标为“历史可读、发布需复核”。

|---|---|---|
| B2-1 正向与无关更新 | D1 完成并附原件 V1 → 生成、核验草稿 → 追加无关备注 | 能从该草稿定位 D1、V1 和核验人；无关备注不改变发布资格。 |
| B2-2 原始反例 | D1 用 A 完成 → 草稿已核验 → 重开纠错 → D2 用 B 完成 | 重开时旧稿失去资格；D2 再绿后仍显示“依据 D1，须核验 D2”，不能自动发布。 |
| B2-3 同路径换证 | 同一引用路径从 V1 换到 V2 → 重跑检查 | 指出哪份依据、哪些步骤受影响。若 V1 仍可授权读取，可重放历史；不能把 V2 当成当时看过的 V1。未变的其他步骤保留原证据。 |

## C1　零授权时如何建立第一笔可信根授权

**高严重度，限定于某项能力没有任何合法持权者的初态。** 依据普通转授规则，每个签发者必须先拥有该能力。因此从空集出发，无论转授多少次都得不到首名持权者。SPEC 赋予 Owner 裁决职责，却未规定某位 Owner 天然拥有所有业务数据。下面是建议客户确认的立权程序，不预设某个账号、岗位或机器自动获得业务权。[Owner 职责](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L144-L149) · [零授权及授予前提](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L565-L588) · [角色和级联规则](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L641-L663) · [当前签发边界](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/internal/envelope/gate.go#L35-L51) · [跟踪议题 #76](https://github.com/Jivan-sky/ai-native-company/issues/76)

### 谁签第一笔，凭什么签

**权威来源是客户组织。** 由对该业务域拥有治理权的客户决策机构或责任人，通过其既有决议、书面委任或已生效的内部审批，指定可核验身份的自然人代表组织签发。委任证据要能核对组织、授权方、签发人身份、可创设的能力和范围、有效期及可撤回者。客户若已指定业务 Owner，可以由该人签发，但必须能从客户提供的独立依据查到这项委任。首次接入时用客户已认可的身份及文书验证渠道确认委任；申请人自行上传一份声称有权的文件不足以建立信任。沿用客户已有的审批人数和权限要求，不额外假定双人审批。

系统将**有限的根签发资格**与**实际业务 grant**分开。登记委任本身不赋予读取、写入、调用或无限转授权限；具备根签发资格的人才能在委任范围内创建首笔业务 grant。管理者 bot 可递交提案，技术管理员可装机，但创建事实必须能归因到受托签发人的已验证决定。若客户无法给出独立的立权依据，列出缺失材料，该能力保持零授权。

### 从签发到撤回

| 转移 | 前提、写入与可观察结果 |
|---|---|
| 零授权 → 待签发 | 固定组织、受予主体、规范化动作与客体、可转授范围、开始与可选截止时间、用途和委任引用/版本。验证签发人当前身份、委任有效性以及客户已要求的审批。准备、预演和点头记录均不使业务权生效。 |
| 待签发 → 根授权生效 | 在权威控制面以一次持久提交写入独立类型的根签发事件：根 ID、无父项、委任及证据版本、已核验签发人、受予人、限制条件、决定时间和生效版本。按组织和立权请求 ID 去重，相同内容重送返回同一根；同请求异内容报冲突。对同一“首次立权”位置做版本比较，竞争提交最多一笔赢得该位置；后续有意设立独立根须有独立依据。 |
| 根生效 → 普通委派 | 子 grant 保存实际依据的父 ID，仅能覆盖父项允许的动作、范围、期限和转授资格。跨域行使按 A3 从叶子回溯到受信根；任一段断裂都不得靠“我是管理员”或“存在同名岗位”补齐。 |
| 生效 → 撤回或到期 | 客户在委任中指定的撤权人或上级治理主体，按既有身份渠道核验后，追加指向根 ID 的撤回事件，记录原因、证据和权威生效版本。撤权权威独立于被撤的业务能力，避免首位持权人离职后无人有权收回。到期按 A3 的时间边界。旧根和所有历史行保留。 |
| 撤回后 → 后续行使 | 在生效点后开始的每次行使，凡唯一依据链经过该根均拒绝，包含子孙多层和代表该人的 Bot；不等待遍历改写所有子文件。独立有效链可单独支持持权人的新行使，旧子 grant 不能自动改挂其他根。重新立权生成新根 ID；要恢复委派须有新的明确依据。 |

**委任的撤销也要说明影响。** 建议客户在委任时明确“撤销未来签发资格”和“同时终止据此签发的存量根”的适用条件。针对具体根的撤回总是使该根链失效。若根的效力明确依赖在任身份或持续有效的委任，离职或委任终止即按条件使存量根及其后代失效；若客户明确以组织名义签发、允许存续，原签发人仍不能再签新根，存量由已指定撤权主体负责。这一区别应写进根事件可核对的依据，缺少约定不推定永久存续。

**留痕与恢复。** 根事件及撤回事件进入 vault 的权威授权历史，查询可还原“谁代表哪个组织、基于哪版委任、在何时授了什么、何时为何撤回”。普通日志只存受控证据引用，原始文书与身份材料按授权访问。权威提交须同时保有足以恢复审计的持久资料；提交前失败保持零授权，提交后单个审计投影失败显示“已生效、审计待补”，恢复只补原事件。重复撤回返回既有结果。不能确认是否看见最新撤权版本时，按 A3 返回无法判定并停止新行使；C2 所述的周期拉取本身无法保证上游即时生效。

## C2　撤权从何时生效，离线副本如何处置未执行动作

**高严重度 · 权威决定与周期复制的时间差。** 副本刚同步到 v10，随后权威端在 v11 撤回 G。在下次同步前，副本看到的文件与“从未撤回 G”完全相同。即使 A3 的委派判定完全正确，重读本地文件也无法区分这两种历史。SPEC 把 Git 设为发布总线，文中给出 15 分钟拉取间隔，同时要求撤权即时生效；间隔描述的是同步节奏，断联时连这个延迟上界也不能保证。[Git 发布模型](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L74-L81) · [同步周期](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L343-L350) · [级联与即时撤回](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/SPEC.md#L644-L663) · [当前信封从本地加载组织事实](https://github.com/Jivan-sky/ai-native-company/blob/20464cc29a20852f8107b1af6a17f029b7360257/runtime/envelope.go#L949-L958) · [跟踪议题 #77](https://github.com/Jivan-sky/ai-native-company/issues/77)

### 生效契约：一个组织、一条权威顺序

**建议采用严格撤权语义。** 由客户指定一处权威授权写口，将经核验的撤回事件和完整授权快照发布为同一笔有序、持久的变更。其提交成功的瞬间为生效点 T，提交回执给出组织、撤回事件 ID、受影响的 grant、前序和新授权版本 R、对应 Git 修订、权威提交时间。R 可以用权威端单调序号绑定不可变 Git 修订，也可以用有唯一前序的授权发布记录表达。Git SHA 用于辨认内容，先后取自权威历史。草稿、审批点击、客户端时间、作者时间及副本拉取时间都不能代替 T。若以 Git 作为权威写口，应将生效点具体落实为**指定授权引用成功推进到经验证修订**；尚未发布的普通提交没有撤权效力。写入方超时而提交结果未知时，按撤回事件 ID 查回原回执，不重复创设另一个生效点。

**并发时按业务边界排先后。** 把撤回提交与每一个受保护动作的开始放在同一个可串行裁决的出口。对读取，边界是服务端不可撤销地开始释放受保护数据；对有副作用的调用，边界是向受控出口作出不可撤销的交付。预检、写入普通队列、领取任务或签一张可离线复用的票都不足以越过该边界。出口须在这一边界校验权威版本、有效链、当前期限和请求的主体、动作、客体，并持久关联操作 ID。检查与交付之间若还能插入已生效的撤回，就须让接收方在执行时核对版本围栏，或由同一权威出口串行完成最后检查与交付。仅在发送前多查一次仍有竞态。

- 撤回先于动作开始：按 R 或更高的完整版本重新判；若唯一依据已撤，拒绝。若另有独立有效链且请求的主体、范围与动作均未改变，允许时记录新依据。显式限定只可使用 G 的请求不能改挂其他根。
- 动作已在 T 前不可撤销地交付：保留当时许可及事实，外部完成时间可晚于 T。长流程的下一次读取、下一笔写入或可分割的后续动作要重新裁决。已经交付的动作不能报告成“已成功拦截”；撤权本身也不授权自动逆转既有副作用。
- 若连接器只能先收一个本地任务、稍后自行发起真正动作，仍在排队阶段。无法提供可靠执行边界的离线连接器，在严格模式下不得自主启动这类动作。这里的代价是断联时暂停受保护的新行使；已保存的非敏感任务元数据仍可展示。

### 重连后的对账与恢复

1. **确认同步断点。** 读取本地最后完整应用版本与权威头，验证组织一致、前序连续且快照完整，再原子切换本地授权视图。丢了中间版本可从可验证快照重建当前视图；历史差异仍需从权威事件补齐。版本倒退、分叉或缺少可信头时保留最后已知现场，继续暂停受保护动作。旧备份不能使已撤的根复活。
2. **逐笔分类。** 按原操作 ID 连接入队记录、执行边界回执、A5 审计及下游回执。明确未开始且仍合业务条件的任务，在当前权威版本和当前时刻重新判；合法者沿原业务幂等键至多交付一次，被撤者留下原因和版本。已取消、已替换、已完成的任务不能因重连而复活。已开始或结果未知的只查结果并补账；下游既无可查回执又无可靠幂等语义时保留待核对，不盲目重发。
3. **分开复原历史与决定下一步。** 用权威顺序判断当次动作相对撤回是先、后还是证据不足；保留原始观察时间、授权版本、动作结果与后补记录时间。若发现撤回后有旧版本副作用，标出受影响对象、依赖链和待处置责任人，不能用现在的拒绝覆盖过去的实际执行，也不能自动报已回滚。需要补偿的动作独立授权。
4. **明确对账何时完成。** 输出断点版本区间、逐笔操作清单及互斥的处置结果：已完成、重新获准待执行、因撤权停止、仍待判断、结果或历史待核对。每个操作须有归属；未决项列出下一步。以持久的操作/事件 ID 及同步游标支持重启续办，重复回放不再增加业务执行或同一审计事件。追平只是本次对账的条件，每个新动作仍须在执行边界确认当下权威状态。

### C2 验收

以组织的贸易域读权或一笔需授权的外部写为样例，初始 v10 有效，v11 撤回唯一依据 G。统一核对四项：调用方回执、队列状态、权威裁决/审计版本、实际数据释放或下游执行次数。

| 编号 | 最小事件顺序 | 验收预期 |
|---|---|---|
| C2-1 生效前后与同秒竞争 | 撤回已获审批但未提交 → 一笔行使；再让撤回和另一笔行使在同秒竞争，分别安排两种提交次序 | 未提交的审批不提前撤权。动作边界在撤回前可依 v10 放行；撤回先提交则按 v11 拒绝，受保护输出 0。交换客户端时钟不改变结论，回执可解释顺序。 |
| C2-2 上游已撤、本地未拉 | 副本刚同步 v10 → 权威推进至 v11 → 本地重新读取同一文件 → 请求准入 | 能向权威裁决时返回 v11 的拒绝；只能读 v10 时返回无法判定。两条路径实际执行均为 0，不能用“刚同步过”证明允许。 |
| C2-3 离线与权威超时 | 有 v10 缓存和未过期租约 → 断联；另一次网络在线但查不到可信头 → 新请求到达 | 两种情况都不以旧权释放数据或产生副作用。允许的意向收件只显示“已收待核验”；用户能区分无法确认和已知撤权。 |
| C2-4 入队后撤权 | v10 准入并入队 → v11 撤回 → 工作器领取；分别在离线、同步恢复时尝试执行 | 离线时保留原任务并暂停；恢复后用 v11 重判为撤权停止。收件仍可追溯，执行次数 0。 |
| C2-5 查权与交付之间撤权 | 工作器最后一次普通查询返回 v10 允许 → v11 生效 → 工作器尚未越过执行边界 | 受控出口拒绝旧版交付，或下游围栏拒绝开始。记录尝试及实际 v11，外部动作 0。仅出示先前预检回执不能通过此项。 |
| C2-6 已开始、回执迟到 | 动作已在 v10 越过执行边界 → v11 撤回 → 下游成功回执迟到或丢失 → 流程要进入下一步 | 前一步如实标为已开始或待查；收到有效回执后补为已完成，不重发。下一独立受保护步骤重新判权并拒绝。 |
| C2-7 断点恢复与重复同步 | 离线队列内分别有被撤任务、依据独立链仍有效的任务、已取消任务与结果未知任务 → 追平并重复恢复两次 | 分别停止、按有效链至多执行一次、保持取消、按原号查结果。处置覆盖每条任务；相同业务执行和审计事件计数不增加。 |
| C2-8 快照损坏或倒退 | 副本只收到 v11 的部分文件，或从 v10 备份恢复；连接后发现缺前序或分叉 | 不对外报告已追平，不根据半份快照放行。验证并切换权威快照后才可重新判；历史缺段另列待补。 |
| C2-9 结果未知与历史差异 | 撤回响应丢失后重送；另发现旧实现曾按 v10 发出一笔动作，其边界晚于 v11 生效 | 同一撤回事件只生效一次。旧动作列作已发生的异常或证据不足；用下游事实核对、保留原账，不报“当时已拒绝”，不自动补发或撤销。 |

建议先修 A1、A2 并用上述故障序列验收。授权部分先明确 C1、C2 的权威来源和生效时点，再统一 A3、A4 的执行与测量判据。验收这些修复时，分别对账终态、审计、证据版本和用户可见结果。
