# 前端诊断：拿专业标准量一遍我们的看板

2026-11-14 · 参照物是一份数据密集型后台（CRM / admin / analytics）的施工规范
（[CRM & Admin Dashboards](https://github.com/Eneryleen/ai-web-design-codex/blob/main/03-site-types/crm-admin-dashboards.md)，
源流是 Tufte 的 data-ink、NN/g 的编码与状态研究、WCAG 2.2），加上 Linear/Vercel 那类"工艺型"产品的做法。

**先说结论：我们做的是一个"编辑式阅读页"，而用户需要的是一个"数据操作台"。**
这两者的排版规则几乎相反 —— 前者靠留白与叙事，后者靠密度与层次。这不是审美问题，是**场景判断错了**。

---

## 一、先判定：我们属于哪一类界面

规范给了一把尺子：**看一次会话多长**。

| 会话时长 | 用户意图 | 该用的策略 |
|---|---|---|
| < 2 分钟 | 扫一眼、点一下 | 移动优先、大按钮、低密度 |
| 2–30 分钟 | 操作型任务 | 平衡；响应式网格、中等密度 |
| **> 30 分钟** | **分析型工作** | **密度优先：多面板、键盘、对比视图** |

我们的看板是给谁用的：车队负责人每天开着它看"谁卡住了"、审计员翻 53 条记录、
运营对着 8 个 case 找卡点。**这是 >30 分钟的场景。**

我们现在的形态：单列 744px、每页 700–900 字符、大留白、段落式说明。
**这是 <2 分钟场景的形态。** 一屏能放的信息量，只有该放的三分之一。

---

## 二、逐条对照（规范 → 我们 → 差在哪）

| 规范要求 | 我们现在 | 差距 |
|---|---|---|
| 顶部 3–5 个 KPI，每个有 值 + 对比 + 趋势 + 基准 | 总览有 3 个数字（3 bot 红 / 0 待批 / 1 项目），**只有值** | 没有对比、没有趋势、没有基准 → 读者无法判断"这是好还是坏" |
| 5–7 个主指标，超过就拆分/按角色分 | 9 页，每页若干指标，没有"主指标"与"明细"的分层 | 没有主次，什么都一样重 |
| 表格：左对齐文本、右对齐数字、等宽数字、sticky 表头、冻结首列 | 审计 53 条用"一行两条"卡片；记录 29 条也是卡片 | 没有表头、没有冻结列、没有排序、没有分页 → 53 条只能靠滚 |
| >200 行分页，2000 行虚拟滚动 | 审计一次拉 500 条全渲染 | 现在 53 条没事，客户现场 5000 条会卡 |
| 每个 widget 自己的"最后更新" | 全局一个 `生成 时间`（今天刚加了 30 秒轮询） | 一个源卡住时，整页看起来都旧 |
| 空 / 载入 / 错误三态都要设计 | 有 empty / unknown，**但错误态没有"重试"动作** | 读者卡在"答不了"，没有下一步 |
| 导航 5–7 项，超过是信息架构问题 | 左侧 9 项 | 分组有问题（见下） |
| 区块标题是短名词，解释放副标题 | 标题是整句：「全部项目在跑的在上；周期过了不等于做完了」「gateway判活 = 真拨一次 socket…」 | 标题不能扫，只能读 |
| 颜色不是唯一信号 | band 点 + 文字标签 | ✅ 这条我们做对了 |
| 键盘可达、命令面板 | Ctrl+K 有；表格无行导航 | 半条 |

## 三、更刺眼的问题：功能做出来了，界面没露

这是"体验差"的更深一层：**用户看不到我们有的能力。**

| 后端已经有 | 看板上的入口 | 结论 |
|---|---|---|
| `anc authz init/grant/revoke/check`（授权签发与撤回） | 无。授权页只能看列表 | 最重要的治理动作看不见 |
| `anc task route`（派单候选与分档） | 无 | 刚做的能力没露 |
| `anc distill draft/check`（草稿与发布校验） | 只有只读的"资产"页 | 生成与发布都没入口 |
| `anc bench`（就绪基准） | 无 | 验收工具完全隐形 |
| `anc apply/probe/notify`（装配、探活、告警） | 系统页只读展示 | 只能命令行 |
| `anc envelope serve`（收件与外部协作） | 运行页有"接入"标签 | 半露 |
| `anc task settle/handoff` | 待批页有决定按钮 | 露了 |

**一句话**：命令行有 20 多个动作，界面露出不到一半。所以"功能有没有全展现"——**没有，差得还不少。**

---

## 四、该怎么办（按改动代价分三档）

### 第一档：不动结构，先修"读不懂"（1–2 天）

1. **每页标题短句化**，长解释降成副标题（9 页同一处模板）。「gateway判活 = 真拨一次 socket…」→ 标题「运行健康」，副标题保留那句话。
2. **错误态给动作**：每个"答不了"配一个"重试 / 去修 org"的按钮，而不是只写一段话。
3. **KPI 补上下文**：每个大数字旁边补「对比（上期）」「基准（目标）」「趋势（sparkline）」。没有数据的就明确写"没有基线"，不许留空。

### 第二档：把"卡片列表"换成"可操作表格"（3–5 天）

4. 审计 / 记录 / 成员三页改用真表格：sticky 表头、冻结首列、右对齐数字、等宽数字、列排序、每页 50 行 + 总数。
5. 密度控制（紧凑/常规/宽松）+ 视图状态进 localStorage。
6. 每页的过滤状态进 URL（现在只有部分页做了）。

### 第三档：把藏起来的能力放出来（按周算）

7. **授权页**加"签发 / 撤回"入口 —— 这是 C1/C2 的操作面，现在只能命令行。
8. **运行页**加"派单预演"（`task route` 的 dry-run 结果直接画成候选档位）。
9. **资产页**加"生成草稿 / 发布前校验"两个动作。
10. **系统页**加 `probe` / `notify` 的触发按钮（默认 dry-run，和命令行同一套）。

## 五、为什么这次不是"再画一版更好看的"

前面几轮我改的是**样式**（间距、字号、配色），那些是"看起来像不像一个产品"。
这一次改的是**信息密度与操作落点**，它决定"这个产品能不能天天用"。

判断标准也换了：

| 旧标准（我之前用的） | 新标准（这次要用的） |
|---|---|
| 版面是否规整、留白是否舒服 | 一屏能不能回答三个问题 |
| 有没有空白页 | 每个数字有没有对比与出处 |
| 卡片是否对齐 | 53 条记录能不能三秒定位到一条 |
| 颜色是否统一 | 能不能不动鼠标完成一次审批 |

---

## 六、先做哪一步

**第一档 + 第二档的表格化**，因为它们是"同一个错配"的两面：
密度不够 + 该用表格的地方用了卡片。

第三步（放能力）要等前两步稳定 —— 否则新入口会长在一个站不住的地基上。

## 七、还没验证的

- 这套规范来自"数据密集型后台"，我们的页面有一半是叙事型（总览、项目）。**不能一把尺子量到底**：
  总览该保留一点叙事，审计/记录/成员必须是表格。
- 真用户测试一次都没做过。上面所有判断都是拿规范对着我们看，不是拿人对着我们看。
