# 长程任务：上下文与权限治理（可执行的定义）

> 这份是**任务定义**，不是文章。开工前读 `docs/GOVERNANCE-FLYWHEEL.md`（背景与判据）。
> 目标：把 ANC 的上下文、权限、决策/卡点/突破，治理成一台能自己转的飞轮。
> 时长：多轮，不设上限；**但每一轮必须有可验收的产出**。

---

## 一、任务目标（一句话）

让系统能回答三个问题，并用答案改进自己：

1. **这个 Agent / 这个人，现在能碰什么？**（权限的单一视图）
2. **它拿到的上下文，为什么是这些？**（装配可解释）
3. **上一次踩过的坑，这次有没有被避免？**（经验真的在回流）

达成标志：这三问在界面上有入口，在账本上有证据，且**第三方按 12 条判据逐条验得过**。

## 二、边界（越界即失败）

**只做这些**
- Go 运行层：字段、事件、判定、导出
- 前端：把已有能力露出（不新造业务规则）
- 文档：规范、判据、人机分工卡

**不许做**
- 不许改后端业务规则去迁就界面
- 不许自动生成"经验"并直接生效（必须人工确认）
- 不许为了好看而加页面；**每加一个页面，先答它是上面三个问题里的哪一个**
- 不许把"按人查"做成"按人记"（账本按角色归因）

## 三、不可谈判的四条

1. **证据链不断**：任何结论都能回指到 `文件:行号` 或事件 id。
2. **单一入口**：权限判定只允许 `org.Exercise` 一处；新增判定点必须删掉旧的。
3. **失败要留痕**：被拒、超时、撤权导致的停止，都要有记录与原因。
4. **门禁优先于进度**：任何阶段不通过门禁，不进下一阶段。
5. **排序原则不可配**：客户可以改"多严重算严重"，不可以改"影响 > 频次"。
   这条是被执行者点出来的：一旦权重可配，各团队必然把频次调到最大，飞轮三个月就变成废话池。
6. **跨人/跨客户的数据，动之前先问人**：删得掉不等于撤得回。

## 四、执行顺序与门禁

| 阶段 | 要交付 | 门禁（不过不许进下一步） |
|---|---|---|
| **P0 盘** | 五类对象（C/D/B/R/E）现状盘点表：每类至少一条真实样本，标出缺哪些字段 | 抽 3 条样本，能指出缺字段 |
| **P1 规** | 字段规范 + 评级公式（写进 `metrics.md`，客户可改） | 12 条判据里的 1/2/4/5 可复验 |
| **P2 治** | `derived_from` 血缘贯通；卡点/突破的录入入口 | 判据 1/3 可复验 |
| **P3 管** | 经验候选 → 人工确认 → 部署（带版本、可回滚） | 判据 7/8 可复验 |
| **P4 用** | 部署到 skill / agent 手册 / 规则；月度回流对比 | 判据 12 + 一次真实月度对比 |

## 五、每一轮的固定动作（不许省）

1. **先读**：`GOVERNANCE-FLYWHEEL.md` 第四节（15 条判据，**当前只有判据 6 成立**），确认这一轮要动哪几条。
2. **再写**：本轮要改的字段/接口/页面，先写成 diff 计划（改哪个文件、为什么）。
3. **后验**：
   - `bash dev/dev.sh all`（fmt/vet/test/交叉/烟测）
   - `bash dev/dev.sh types`（只拦"前端编字段"，**不拦破坏性变更** —— 别把它当契约门禁）
   - `bash dev/dev.sh ui`（界面不变量）
   - 本轮动到的判据，逐条跑 4.4 那套命令，贴输出
4. **留痕**：commit message 写清"这一轮动了哪条判据、怎么验的"。
5. **自审**（每次交付末尾，必写）：
   - 有没有改动后端业务规则去迁就界面？
   - 有没有自动生成并生效的"经验"？
   - 有没有新增无法回指证据的结论？

## 六、什么时候必须停下来问人

- 要引入**新的治理对象**（第五类之外的）
- 要把"按角色归因"改成"按人归因"
- 要让**自动生成的经验**直接生效
- 判据之间打架（例如：可解释性要求记 why，但隐私要求不记原话）
- 连续两轮在同一处修不动（说明模型错了，不是代码错了）
- 要动「影响面 / 频次」的排序规则（见不可谈判第 5 条）
- 要把别人的客户数据带进别人的视野（见第 6 条）

## 七、用多角色自测（每完成一个阶段做一次）

派三个 subagent，各自独立读同一份产出，**互不通气**：

| 人设 | 只许问 | 输出 |
|---|---|---|
| 体验者（行政/文科，不懂技术） | 我看不看得懂？下一步做什么？ | 复述一遍任务卡；复述不清就是失败 |
| 执行者（一线负责人） | 够不够我拍板？ | 列出"我还缺哪三条信息才能决定" |
| 策划者（数据治理/审计） | 能不能被第三方验？哪里自说自话？ | 按 12 条判据逐条打"成立/不成立+反例" |

**取交集**：三个人都通过的才进部署；只有一个人说好，说明只对那一种人成立。

## 八、产出格式（每轮结尾）

```
【本轮】P{阶段} · 判据 {编号}
【改了什么】文件 → 改动 → 为什么
【怎么验的】命令 → 结果（贴关键输出）
【没做/做不到】如实列，写清卡在哪
【下一轮】一句话
```

## 八之二、判据的写法（硬规定）

每条判据必须四元组齐全，缺一项不许进验收表：

```
判据 N · 对象 X · 字段/端点 Y
样本框  范围 + 确定性抽样（例：最近 200 条，按 id 字典序取前 20）
命令    一条能跑的命令
期望    退出码 + 字段断言
现状    成立 / 不成立 / 无法判定
```

写了"我们会注意""后续优化"的，一律视同没写。

## 九、反模式（见到就停）

- 为了"显得完整"加空壳页面
- 把判据写成"我们会注意…"（不可检验 = 没写）
- 用一个新机制绕开旧机制（两套判定并存）
- 把"经验"写成鸡汤（没有证据链、没有适用范围、没有反例）
- 用"后续优化"结束一个阶段
